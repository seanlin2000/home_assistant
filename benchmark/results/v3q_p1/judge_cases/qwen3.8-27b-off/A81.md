# Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: Good question, and one where the honest answer is "it depends on the architecture," but there's a solid general picture. Let me walk through it.

What stays local: the model weights themselves never leave your machine. The entire inference process — token generation, attention, context window management — happens in your RAM and GPU or CPU. Your conversation history, system prompts, any personal data you've fed into the context, and the model's "thinking" about how to answer all stay on your hardware. That's the whole point of running locally: no one else sees what you asked the model or what it produced.

What gets transmitted: this is where it gets nuanced. When the model decides to call your web-search API, it sends a query string — usually a natural-language question or a set of keywords. That query is visible to the search provider in full. Depending on how you've wired things up, they might also see:

- Your IP address, which can be tied to your general location and sometimes your ISP account.
- Any headers you send, which could include API keys (that's fine, it's yours) but also accidentally include user identifiers if you're not careful with how you build the request.
- The specific endpoint URL or parameters if you're using a less common search service.

What typically does NOT get transmitted: the model's internal reasoning, your full conversation context, the system prompt, and any other data in the context window that isn't directly part of the query. A well-designed local setup only sends the minimal search string. However, if you've written a wrapper that, say, prepends "The user is asking about their medical history regarding..." to every query, then yes, that goes out. The risk is entirely in how *you* construct the outgoing request.

One more subtlety: some local model frameworks have built-in "tool-calling" patterns where the model emits a structured JSON call like `{"search": "best espresso beans 2026"}`. In that case, only that JSON payload leaves your machine. But if you're using a framework that proxies through an intermediate service — even a local one with a cloud fallback — check its network activity. Tools like Wireshark or just `lsof` on Linux can show you exactly what sockets are opened and what's going over the wire.

How to minimize exposure:

First, strip the query down. Before sending it to the search API, run a quick local filter that removes names, addresses, account numbers, or anything that isn't essential to the search. A simple regex pass or even a tiny local classifier can catch most of it.

Second, use a privacy-focused search backend if you can. SearXNG is an open-source metasearch engine you can self-host; it queries multiple engines but sits on your own server, so the query only reaches Google or Bing via SearXNG
