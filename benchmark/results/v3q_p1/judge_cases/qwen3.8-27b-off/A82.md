Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Great question — this is something I think about a lot. Let me take it in layers.

**API** is the broadest term. An API is just a contract: "send me data in this shape, I'll give you back an answer in that shape." It could be HTTP with JSON, a command-line interface, even a function call inside a process. APIs don't care who's calling them — a human in a browser, a server, or an LLM. The web search engines and page-fetching services already expose plain HTTP APIs today.

**A software tool** is the thing that actually does work for you: a script, a CLI program, a library function. A tool is concrete and self-contained — it takes input, produces output. In the LLM world, "tool" usually means something the model can invoke, but conceptually a tool predates that idea by decades.

**An MCP server** sits in between. MCP — Model Context Protocol — is an open standard for connecting AI systems to external capabilities. An MCP server *wraps* tools and data sources behind a standardized protocol: it advertises what tools exist, what their parameters are, and how to call them, using JSON-RPC over stdio or HTTP. The key difference from a raw API is that MCP is designed specifically for LLM consumption — the tool descriptions, schemas, and error formats are shaped so a model can discover and use them without bespoke glue code. One MCP server can expose dozens of tools, and any MCP-compatible client can pick it up unchanged.

Now, the architecture for your local-LLM web search system. I'd do it in three layers:

**Layer one: the capability layer.** You need a search provider and a page-fetcher. For search, you could call a public API like SerpAPI or Brave Search, or run something local like SearXNG if you want no external dependencies. For fetching, a simple HTTP client with HTML-to-markdown conversion (something like `trafilatura` or `readability`) is enough. These are just plain tools — scripts or functions that take a query or URL and return results.

**Layer two: the MCP server.** You wrap those capabilities in a small MCP server exposing three tools: `web_search(query)`, `fetch_page(url)`, and maybe `summarize(text)` if you want the summarization to be a tool rather than something the model does inline. The server handles the messy parts — rate limiting, caching fetched pages so the model doesn't re-fetch the same URL, truncating long pages to fit context windows, sanitizing HTML. This is where MCP earns its keep: your local LLM client just needs to know "there's an MCP server at this endpoint" and it can discover the tools automatically.

**Layer three: the orchestration.** Your local LLM — let's say running via Ollama or llama.cpp
