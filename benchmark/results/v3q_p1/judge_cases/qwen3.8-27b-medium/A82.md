An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Good question, and the three terms live at different layers, which is why people conflate them.

An API is a communication contract between two programs. It says what calls exist, what shape the requests and responses take, and how you authenticate. A web search service's API, for instance, is something like: send a query, get back a JSON list of results. It's aimed at code writing developers, and it knows nothing about LLMs.

A software tool is just a piece of software that does a job — a script, a command-line program, an app. In the LLM world the word takes on a more specific meaning: a tool is a callable function that a model can invoke, usually described by a name, a description, and a JSON schema of its inputs. When a model "uses a tool," it's really just emitting a structured request that some surrounding program executes and hands the result back.

An MCP server is the newest layer: a standard protocol — Model Context Protocol, created by Anthropic and now widely adopted — for packaging capabilities so LLM applications can discover and use them. An MCP server exposes tools, plus data it calls resources and reusable prompts, over a simple transport like stdio or a local HTTP endpoint. The important difference from a raw tool is discoverability and standardization: the client can ask the server "what can you do?" and get back self-describing tools with schemas, so any MCP-compatible client — Claude Desktop, Open WebUI, a custom agent loop — can plug in the same server without custom integration work. Most MCP servers are honestly just thin wrappers around ordinary APIs, adding the AI-facing packaging on top.

So: APIs are the plumbing, tools are the callable units, and MCP servers are a standard, self-describing container for tools aimed at LLM clients.

Now, your architecture. The key insight is that summarization isn't a tool at all — that's what the LLM itself is best at. You only need two tools: web search and page retrieval. Here's how I'd build it.
