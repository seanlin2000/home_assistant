ASSISTANT: Quantizing a model means storing its weights with fewer bits than the training precision, which is usually 16-bit floating point. A 70-billion-parameter model in FP16 needs about 140 gigabytes just for the weights, since each parameter takes two bytes. In 4-bit you cut that in half to roughly 35 gigabytes, and in 2-bit you cut it again to about 17.5 gigabytes. If we're talking 8-bit, that's about 70 gigabytes.

A few caveats on those numbers. The pure arithmetic is a floor, not what you actually see on disk. In a real GGUF file from llama.cpp, weights are stored in blocks, each with its own scale factor and sometimes zero-point, so a 70B model quantized to 4-bit typically comes out around 40 to 42 gigabytes rather than 35. Newer formats like IQ4_XS get closer to the ideal, around 38 gigabytes. And some layers, such as embeddings and normalization parameters, are usually left at higher precision because they're disproportionately sensitive. On top of all that you need room for the key-value cache, which grows with context length, plus activations and framework overhead, so the memory you actually need to run it is meaningfully more than the file size.

The mechanics: quantization maps a continuous range of floating-point values onto a small set of discrete levels, four bits giving sixteen levels per group. In practice it's almost always group quantization, where each block of a few dozen or a hundred weights shares its own scale, so regions with small weights aren't wasted on a global scale. Methods like GPTQ, AWQ and GGUF's k-quants also use a small calibration dataset and approximate second-order information about which weights matter most, then round them in a way that minimizes the resulting output error rather than just rounding naively.

The trade-offs. The headline one is that 70-billion-parameter models tolerate 4-bit surprisingly well. Benchmarks consistently report perplexity degradation of about one to three percent versus the full-precision model, and one commonly cited figure for Llama 3.1 70B at Q4_K_M is around a 1.5 percent relative perplexity increase. The general rule the community has settled on is that quality loss shrinks as model size grows, so 4-bit is close to lossless on a 70B model and noticeably lossier on a 7B model. Some reasoning and code benchmarks show more degradation than perplexity does, in the range of five to seven percent, so "nearly lossless" means on average, not on every task you happen to care about.

Two-bit is a different story. Naive 2-bit quantization, just rounding weights into four levels, can destroy a model outright, with perplexity exploding to numbers that mean the model is generating nonsense. What makes 2-bit viable at all is handling outliers: a transformer has a small number of weights that are much larger in magnitude than the rest, and methods like SpQR, QuIP#, AQLM and Mamba-style codebook quantization either store those outliers separately at higher precision or use learned vector codebooks instead of scalar rounding. Even then you lose accuracy, and the loss is not recoverable by fine-tuning the quantized model back up.

Speed is the counterintuitive part. Inference at these sizes is usually bound by memory bandwidth, since you read every weight once per generated token, so smaller weights generally mean faster generation. A 4-bit 70B model typically runs faster than its 16-bit version and can fit on hardware that couldn't hold it at all, which is the whole point: a 4-bit 70B model needs two consumer GPUs or a 48 to 64 gigabyte card, while 2-bit gets you into the range of a single high-end card or a lot of system RAM. But 2-bit formats often add unpacking and lookup-table overhead that eats much of that bandwidth saving, so they can end up slower per token than 4-bit despite being smaller.

There are a few more costs worth knowing. Quantization is task-specific and calibration-dependent, so the reference text used during quantization genuinely affects results, and the right way to evaluate is to test the specific quantized model on the workload you care about. A 2-bit model may still chat fluently while quietly dropping factual recall, arithmetic, and long-chain reasoning. You also give up some control: a quantized checkpoint is not something you can meaningfully continue pretraining on, though 4-bit does support parameter-efficient fine-tuning in the QLoRA style. And if you're planning long context, remember the key-value cache is usually kept at 8 or 16 bits and scales with sequence length, so shrinking weights doesn't shrink that at all.

So the practical read: 4-bit on a 70B model is the sweet spot, roughly one-quarter of 16-bit memory for a couple of percent of quality. 2-bit is a real but lossy option for squeezing an unaffordable model onto hardware you already have, and it deserves skepticism until you've benchmarked it on your own tasks.
