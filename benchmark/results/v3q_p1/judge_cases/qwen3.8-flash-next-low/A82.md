Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Think of the three as different layers of the same plumbing. An API is a contract between a program and some service: a defined set of endpoints, request formats, and responses that let software talk to a service over a network. A weather company's forecast endpoint is an API; so is your search engine's query endpoint. It's a general concept that predates LLMs and has nothing to do with them. A software tool, in the LLM sense, is a function the model is allowed to call during a conversation: a named operation with typed parameters, where the model emits a structured request, your code executes it, and the result is fed back into the context. A tool is a unit of agency for the model. An MCP server sits in between. MCP, the Model Context Protocol, is an open standard — introduced by Anthropic in late 2024 and since adopted by other vendors — for exposing tools, resources, and prompts from a standalone server process to any compliant LLM client. It defines how a client discovers what tools exist, how calls and results are transported (typically JSON-RPC over stdio or HTTP), and how to keep the tool implementation separate from the application. So: an API is how programs talk to services, a tool is how a model invokes an action, and MCP is a standardized way to package tools so any MCP-compatible client can use them without custom glue code.

For your system, I'd separate it into four pieces. First, the model host: a local model served through something like Ollama, llama.cpp, or vLLM, chosen specifically for tool-calling support — not every local model is trained to emit reliable function calls, and models like Qwen or Llama tend to be better at this than smaller or less chat-tuned ones. Second, the search step: a real web search API, because a local model has no search capability of its own. Brave Search and Tavily are popular choices since they're cheap and offer free tiers, and some are built for LLM agents. The tool here takes a query string and returns ranked titles, URLs, and snippets. Third, the retrieval step: a fetch tool that downloads a URL, strips boilerplate with a readability-style extractor, and converts the page to markdown or plain text. Raw HTML will choke a small model; extracted text is what you feed it. Fourth, the summarization logic, which is where the actual architecture lives. Web pages are often longer than you want to stuff into context, so the robust pattern is map-reduce: chunk the extracted text, have the model summarize each chunk, then have it merge the chunk summaries into one. For short pages you skip straight to a single summarization pass. You can also wrap this as a higher-level tool — "search and summarize" — that runs the whole pipeline internally and hands the model only a digest, which keeps the model's job simple and saves context tokens.

Where MCP fits depends on who the clients are. If this is one personal script and one model, MCP is overhead: just define the tools as JSON function schemas in your application loop and call Python functions directly. Simpler, fewer moving parts. MCP becomes worth it when you want the same capabilities reusable across multiple clients — a local app, an IDE, a chat UI — or when you want to plug into existing MCP-capable software without rewriting glue each time. In that version, you'd build a small MCP server exposing search_web, fetch_page, and summarize as tools, with an MCP client bridging to your local model's serving endpoint. The tradeoff to keep in mind is context bloat: MCP clients load tool descriptions into every conversation, and search results are noisy, so a well-designed pipeline filters aggressively and returns compact results rather than dumping full pages back into context. My honest recommendation for a hobby build would be a plain tool loop in one process, using Ollama's tool-calling API with three functions — search, fetch-to-text, summarize — and only graduate to MCP if you later find yourself wanting to share those tools across several applications.
