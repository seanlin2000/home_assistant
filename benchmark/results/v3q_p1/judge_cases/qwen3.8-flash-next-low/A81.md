# Question A81 (category A)
What it tests: Privacy architecture of local model plus remote search
Expected search behavior: no
Expected reply: an ordinary answer
Constraints: none
Gates especially relevant here: none beyond the general rules

Reference sketch (what a correct answer must contain):
The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. Websites the assistant then fetches see the IP address and the requests. What stays local: the audio and transcription if speech is processed locally, the full conversation and history, the model's reasoning and answers, and anything never put into a query. Minimizing exposure: keep personal details out of queries (write queries from the question, not the whole conversation), search only when needed, cache results, use a privacy-focused provider or a self-hosted metasearch proxy such as SearXNG, route through a VPN for IP privacy, and check the provider's data-retention terms.

ASSISTANT: Short version: the model stays private, but the query is a leak, and the leak is bigger than most people expect because the search query is derived from your prompt.

Here is the anatomy. What definitely stays on your machine: the model weights, your full conversation, everything you paste into the context window, and any local files the model reads. What leaves your machine, for every single search call, is the query string your agent constructs plus account metadata. That query string matters more than it looks, because a local model tends to write a search query that is a compressed version of what you were just talking about. If you were discussing a specific patient, a client's name, an internal project codename, a file path, a law firm matter, or a stock position, the model will often put those words directly into the query. Alongside it the provider sees your API key, your source IP address, timestamps, request counts, and user agent. So the provider learns when you searched, from where, how often, and roughly what you were working on, even if it never sees your actual prompt. If your setup also does page extraction, add another exposure: fetching the result pages puts your IP in that website's access logs, and some APIs send the full URL or content back to the provider for summarizing, which pulls your document contents into their systems too.

I checked two commonly used providers specifically. Brave's API privacy notice, updated in November 2026, says a record of search queries submitted through your account is retained for a maximum of ninety days for billing and troubleshooting, with your IP address and authentication token logged, and account data kept for twelve months after account deletion, support data up to six years. Brave's claim is that it collects no identifiers linking a query to an individual and it treats queries as not personal data, but it does tie the queries to your account for that ninety day window. A true zero data retention option exists, but as an enterprise tier. They also require payment and billing details for every plan, and their crypto micropayment alternative writes a transaction to the Base blockchain permanently and publicly, which is worse for pseudonymity than a card. Tavily, on the other hand, explicitly says it may share your query data with third party search index providers such as Google when its own index cannot answer, and it has a setting called "allow use of query data" which, if on, means your queries are stored and used to improve their service. Their EU endpoint offers EU query residency with a zero query retention option, but accounts, support, usage and billing data still sit in shared US systems. Other providers vary, and several don't publish API query log retention periods at all, so treat "privacy-focused" marketing as a claim to verify rather than a fact.

To cut the exposure down, the biggest single win is query hygiene rather than provider choice. Instruct the agent to emit keyword-only, generic queries with proper nouns and identifiers stripped, or run a tiny local rewriting step whose only job is to sanitize the query before it goes out, and simply don't route sensitive topics through search at all. Then pick a provider whose terms you actually read, and turn off any "use my queries to improve the product" toggle. If you want the strongest setup, self-host SearXNG, which needs no account, no API key and can log nothing at all, but understand the catch: SearXNG fans your query out to real search engines, so Google or Bing may still see it, which means you should disable those engines and keep only privacy-respecting ones, or put your instance behind a VPN or your own VPS so the upstream engines see a datacenter IP rather than your home connection. A public hosted SearXNG instance is not equivalent to self-hosting, since whoever runs it can log everything.

At the network layer, give the search calls their own egress path, a VPN or a WireGuard tunnel to a box you control, and firewall outbound traffic from the machine running the model so only the search endpoint is reachable. That way a leaked API key or a bug in a plugin can't exfiltrate anything else. Also check how your frontend is wired: Open WebUI, LM Studio and Ollama search plugins differ in whether they send only the distilled query or the whole prompt to the search service, and that single setting changes your threat model completely. Finally, cache results locally and dedupe queries, since fewer calls means less timing and usage metadata about your work, and don't pipe scraped page contents onward to any cloud service. One thing worth saying plainly: you cannot make a hosted search API fully private, because searching is by definition asking a third party a question. The realistic goal is to make the question unidentifiable and the metadata sparse, which the steps above get you close to.
