Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: The three sit at different levels of abstraction, and they nest inside each other.

A software tool is the most general thing. It's just a program that does a job — a script, a command-line command, a library function, a little web app. Its interface is whatever its author happened to choose. "Fetch this URL and hand me the text" is a tool.

An API is a contract for calling something. It doesn't describe what the thing does, it describes the shape of the conversation: what you send, what comes back, the error codes, the format. A web search engine exposes a REST API — you post a query, it returns structured results like titles, URLs, and snippets. So the API is the promise about form; the software sitting behind that API is the tool doing the real work.

An MCP server — Model Context Protocol, the thing Anthropic standardized — is a layer of standardization on top of tools for the specific purpose of feeding them to LLMs. It's a protocol, typically JSON-RPC, that lets an AI client *discover* what capabilities a server offers, read each one's name, description, and parameter schema, and then call it. An MCP server usually wraps tools that themselves call APIs. So the nesting is: a tool does the work, the API is how you talk to it, and the MCP server packages it up with metadata so any compatible LLM client can find and use it without you hand-writing glue code for each one.

Now, the architecture for a local LLM that searches, retrieves, and summarizes. I'd build it in four pieces.

First, the brain: a local model — something like Llama, Mistral, or Qwen — running through a server like Ollama, llama.cpp, LM Studio, or vLLM. This model does the planning and, critically, the summarizing. I want to flag that summarization is not a tool at all; it's a model capability. You don't build a "summarize tool" — you just let the model read the retrieved text and write the summary in its final answer.

Second, an orchestration loop — a small program, Python is the usual choice, that mediates between the model and the tools. It sends the user's request along with the available tool definitions to the model, the model replies with a tool call like "search for X," the loop executes it, stuffs the result back into the conversation, and asks the model again, repeating until the model says it has enough and writes the final answer. If your local client speaks MCP, then *this* program is effectively the MCP client and the loop is built in for you.

Third, the tools themselves. A search tool that hits some search backend — Brave Search, Tavily, a self-hosted SearXNG, or DuckDuckGo — and returns titles, URLs, and snippets. And a fetch tool that takes a URL, downloads it, strips the HTML down to just the readable body using something like trafilatura or a readability library, and returns the text. Those two are your software tools, and each of them is secretly making an API call under the hood.

Fourth, and this is the part people skip: how you connect the tools to the model. For a simple local setup, I'd just expose search and fetch as plain functions in Python and call them from my own loop — simpler than standing up an MCP server. You reach for an MCP server when you want to share those same tools across many different clients or use an off-the-shelf one, which is when the discovery-and-metadata layer pays off.
