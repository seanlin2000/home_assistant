# Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: Good question, and one where the answer depends a lot on how you've wired the pieces together, so let me walk through the general architecture.

**What stays local.** The model weights, the inference, your conversation history, your system prompt, and the final generated answer all stay on your machine. If you're using a framework that lets the model reason about what to search for, that reasoning step also stays local. None of that touches the network unless you explicitly put it into a request.

**What gets sent to the search provider.** The critical piece is the query string. In a typical setup, the local model formulates a search query and your code sends it to the API. That query is the main thing the provider sees. In addition, virtually every API provider logs metadata: your IP address, a timestamp, your API key or account identifier, and whatever headers your HTTP client sends. Some providers also log the results you requested and how many you pulled back.

Here's the important nuance: the query the model generates is often a rephrased version of what you asked. If you ask "what's the best treatment for the rash I got after using that new laundry detergent from Brand X," the model might turn that into a query like "contact dermatitis from laundry detergent Brand X" or it might strip the brand entirely. You can't fully predict what it sends unless you log the outgoing requests yourself.

**How to minimize exposure.** A few practical steps, roughly in order of impact.

First, look at the outgoing query before it leaves your machine. Most local-LLM frameworks let you log or intercept tool calls. If you see the query being sent, you'll know exactly what's going out, and you can add a system-prompt instruction telling the model to keep queries short and generic, with no personal names, addresses, or identifiers.

Second, choose a search API whose privacy policy you can actually read and that commits to not retaining or using queries for training or advertising. A self-hosted meta-search engine like SearXNG is the strongest option here because nothing leaves your network at all, but it's more work to set up. If you want a hosted API, look for ones that explicitly state they don't log query content beyond a short retention window, or that offer a privacy tier.

Third, decouple your identity from the requests. Use a dedicated API account that isn't tied to your name or email, and route the calls through a VPN or a local proxy so the provider sees a generic IP rather than your home address.

Fourth, minimize what you ask the model to look up in the first place. If you can phrase your question in a way that doesn't require the search to include sensitive details, the model's reformulated query will tend to be less revealing too.

The bottom line is that the model itself is private, but the search step is where your information leaves the building, and the query string is the thing you most want to control.
