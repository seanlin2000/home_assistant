ASSISTANT: Short version: everything about your documents and conversation stays local, but the search query itself is a disclosure, and a search query is often a pretty precise description of what you're working on.

What stays on your machine is the obvious part: the model weights, your chat history, any files you feed it, the intermediate reasoning, and the fact that you were the one asking. None of that goes to the search provider unless your agent explicitly puts it in a request. One caveat is that "local" wrappers sometimes phone home with telemetry or crash reports, so it's worth checking what the harness around your model does, not just the model.

What actually crosses the wire is usually four things. First, the query string as your agent constructed it — often just keywords, but in agent pipelines it's common to build a query by pasting a sentence from a document, a client's name, a ticker, a symptom, or a code snippet, and at that point you've handed over the substance of your work. Second, your API key, which identifies your account, so every query is attributable to you even if no name is attached. Third, network metadata: your IP address, timestamps, HTTP user agent, and any parameters you set like count, country, language or freshness, which can narrow your location further. Fourth, the shape of your activity — how many queries, how fast, follow-up refinements — which is itself a fingerprint of the task.

Provider-side, that typically lands in request and billing logs with some retention window. Here's the thing to watch, though: many "AI search" APIs are not search engines at all but scrapers sitting on top of Google or Bing. With those, your query is forwarded live to a Big Tech engine, which logs it under its own retention policy, one you have no control over and no way to request deletion from. Brave is one of the few vendors with an independent index and it sells a Zero Data Retention tier on that basis, which is architecturally real. But I'd still read the fine print: one fact-check of Brave's API privacy documents reported that queries submitted through a Search API account are retained up to 90 days for billing and troubleshooting, which is not the same as truly nothing stored. I couldn't verify the current wording of every vendor's policy, so treat the retention claims as something to confirm in the data processing agreement, not something the marketing page settles.

One more leak people miss: if your agent fetches the pages behind the results, each of those sites sees your IP, and any browser-like headers your fetcher sends. If you use an extraction or "read this page for me" service instead, you've added a third party who logs the URLs it pulled for you. And if you rank results with a hosted embedding model, that content is going out too.

To minimize exposure, the highest-value habit is query hygiene: make your agent synthesize short, generic keyword queries rather than echoing source text, and strip names, numbers, addresses and email strings before a query is built. Keep the API key server-side and rotate it. Prefer POST requests so the query doesn't sit in a URL where proxies and logs can pick it up. Point the outbound traffic through a VPN or a small relay server so the provider sees a datacenter IP instead of your home one, and restrict egress so only the search host is reachable. Pick a provider that owns its index and offers contractual zero retention or a short documented window, or skip third parties entirely and self-host something like SearXNG or Whoogle, which you control and can run with logging off — the tradeoff is that those still query public engines upstream unless you configure them otherwise, so you inherit someone's logs. Finally, cache results locally so the same question doesn't leave your machine twice, and keep your own log of what you sent, because if you ever need to ask a provider to delete something, you'll want to know which queries you made.
