Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

ASSISTANT: Think of the three as different levels of the same stack.

An API is a contract between pieces of software. It says: send a request shaped like this and you'll get a response shaped like that. A REST endpoint, a GraphQL schema, a library function signature, JSON-RPC — all APIs. The audience is a deterministic program that already knows exactly which call to make and what to do with the answer.

A tool is an API aimed at a model instead of at a programmer. It's a callable thing plus three extra ingredients: a natural-language description of when to use it, a typed parameter schema the model can fill in, and the assumption that the model itself decides whether to invoke it and what to do with the result. So every tool contains an API, but the tool wrapping is what turns a capability into something an agent can choose. The other half of a tool is the runtime that actually intercepts the model's request, executes it, and feeds the output back into the context window.

An MCP server is a way of packaging and serving tools. Model Context Protocol is an open standard — the current specification is the July 28, 2026 release, which moved to a stateless protocol core and added things like multi-round-trip requests, an extensions framework and hardened authorization — that lets a program advertise its capabilities to a model host over JSON-RPC, usually over stdio or a streamable HTTP endpoint. A client asks the server what it offers via a tools list, then calls them. MCP exposes three primitives: tools, which the model invokes; resources, which are readable data like files or records; and prompts, which are reusable templates. Its value is standardization. You write the search integration once and every MCP-compatible client — an IDE, a chat app, your own agent — can use it, and you can bolt on servers other people wrote.

For your local web-search-and-summarize system, here's how I'd build it.

The model layer is a local model served behind an OpenAI-compatible endpoint, Ollama or llama.cpp's server work fine, chosen specifically because it supports function calling well enough to survive multiple rounds. A small model that only calls tools reliably in one or two turns will make the whole pipeline brittle, so tool-use quality matters more than raw benchmark score here.

The orchestration layer is a plain agent loop you own: take the question, hand the model the tool schemas, let it emit calls, execute them, append the results as tool messages, repeat until the model produces a final answer or you hit a budget of roughly five to eight calls.

Then the three capabilities. A search tool takes a query and hits a real search backend — Brave Search API, SerpAPI, Tavily, or a self-hosted SearXNG if you want to keep traffic local — and returns a short list of titles, URLs and snippets, deliberately truncated. A fetch tool takes a URL, does the HTTP request with a timeout, strips the HTML down to readable text or markdown, dedupes boilerplate, and caps the payload so a single page can't flood the context window. A summarize tool is where I'd cheat in your favor: rather than dumping a long page into the main model, chunk it and run a map-reduce pass through a small fast local model, returning a compressed summary with the key numbers and quotes preserved.

Wrap those three in an MCP server if you have more than one client that needs them, or if you want to swap in someone else's browser or scraping server later. If it's genuinely just one local app, skip MCP and use direct function calling — one fewer process, one fewer failure mode, and you avoid a class of bugs around tool-name collisions when several servers advertise similar tools. MCP is the right call for capability sharing, not for a single script.

Two things I'd treat as non-optional. First, cache: store fetched pages keyed by URL with a TTL, because agents re-fetch the same page constantly. Second, treat everything that comes back from the web as data, never as instructions. A fetched page can contain text that reads like a command to your model, and a local model with no guardrails will happily follow it. So put fetched content in a clearly delimited message, tell the model that block is untrusted, allowlist or denylist domains if you have opinions, and never let a tool call originate from within fetched content without your loop validating it.
