# The self-hosted voice assistant pipeline in 2026: wake-word → VAD → STT → LLM → TTS, end to end
A voice assistant that never sends your audio to Amazon or Google is one of the most satisfying things you can self-host - and in 2026 it’s genuinely achievable on modest hardware. The pieces all exist as mature open-source components, and the Wyoming protocol (the glue Home Assistant standardized) lets you snap them together like Lego. The result: say “Hey Jarvis, turn off the kitchen lights,” and the entire round trip - wake-word, transcription, intent, response, speech - happens on hardware you own.
But “achievable” isn’t “trivial.” A voice pipeline is five distinct stages, each with its own latency and resource cost, and the user-perceived quality is dominated by the slowest stage and the weakest link. Get the wake-word model wrong and it triggers on the TV; get the STT model too big and responses lag two seconds; route to a cloud LLM and you’ve defeated the point. This guide walks the whole pipeline: what each stage does, what it costs, how they connect over Wyoming, and the decisions that determine whether your assistant feels snappy or sluggish.
## The 30-second answer
- You run Home Assistant and want local voice : useHA Voice (Assist) with the Wyoming add-ons - openWakeWord + faster-whisper + Piper. This is the paved path; it Just Works.
- You want the hardware appliance : theHome Assistant Voice Preview Edition (the official ESP32-S3 puck) handles wake-word + audio on-device and streams to your server.
- You have a GPU : run faster-whisper on it (`small` or`medium` model) and a local LLM via Ollama. Sub-second STT, fast intent.
- You’re CPU-only : faster-whisper`base` or`tiny` model + Piper + HA’s built-in intent matching (skip the LLM for command-style use). Still works; just smaller models. See llama-cpp-tuning-for-cpu-only-homelab-inference.
- You want conversational (not just commands) : add a local LLM hop (Llama / Qwen via Ollama) for open-ended Q&A. Adds latency; worth it for “what’s the weather and should I bring a jacket.”
- You only need a few fixed commands : skip the LLM entirely. HA’s intent matching handles “turn on X” deterministically and instantly.
- You’re tempted to route to a cloud LLM for quality : that’s a real trade - better answers, but your transcribed speech leaves the house. Decide deliberately.
- You want the five-minute version : HA OS + the Wyoming add-ons from the add-on store + a USB mic. The hard part is tuning, not setup.
If your scenario doesn’t immediately match, walk through the pipeline stages below.
## Do you actually need the full pipeline?
Honest gates before building all five stages:
- Do you need conversation, or commands? “Turn off the lights” is a command - HA’s built-in intent matching handles it with zero LLM. “Remind me to call mom when I get home and what’s traffic like” needs an LLM. Most home voice use is commands.
- Do you need a wake word, or a push-to-talk button? Always-listening wake-word is convenient but means a mic is always processing audio. A physical button (or app tap) sidesteps the privacy and false-trigger problems entirely.
- What’s your latency tolerance? Each stage adds delay. A command pipeline can be sub-second; adding a local 7B LLM hop pushes total round-trip to 2-4 seconds. Some people hate that.
- Do you have the always-on compute? STT and LLM models sit in RAM/VRAM. A pipeline ready to respond instantly means keeping models loaded - RAM/VRAM you can’t reclaim.
If you’re past these gates, continue.
## The five stages
``` ┌──────────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ │ wake-word│ → │ VAD │ → │ STT │ → │ LLM │ → │ TTS │ │openWakeW.│ │Silero│ │Whisper│ │Llama│ │Piper│ └──────────┘ └─────┘ └─────┘ └─────┘ └─────┘ always detect speech intent / speech listening speech → text answer → audio bounds ```
### Stage 1: wake-word detection (openWakeWord)
The always-on stage. A tiny model continuously runs on the audio stream, listening for the trigger phrase (“Hey Jarvis”, “Okay Nabu”, a custom word). Everything downstream is dormant until the wake word fires.
- Tool : openWakeWord (the de-facto open standard) or microWakeWord (for on-device ESP32).
- Where it runs : ideally on the satellite device (the puck/mic), so raw audio never leaves it until triggered. Can run server-side too.
- Cost : tiny. Runs on a Raspberry Pi or an ESP32-S3. ~50-100 MB RAM server-side; near-zero on a dedicated DSP.
- The tuning problem : false positives (triggers on TV dialogue) vs false negatives (doesn’t hear you). Adjustable threshold. Custom wake words can be trained but pre-built ones (“Hey Jarvis”, “Hey Mycroft”, “Okay Nabu”) are well-tuned.
### Stage 2: voice activity detection (Silero VAD)
Once woken, the system needs to know when you’ve stopped talking so it can send the utterance to STT. VAD detects speech vs silence and marks the end of the utterance.
- Tool : Silero VAD (lightweight, accurate).
- Cost : negligible - runs on CPU, microseconds per frame.
- Why it matters : without good VAD, the system either cuts you off mid-sentence (too aggressive) or waits awkwardly after you finish (too lax). The “end-of-speech timeout” is the key tunable.
### Stage 3: speech-to-text (Whisper / faster-whisper)
The transcription stage. Takes the captured audio, produces text.
- Tool :faster-whisper (CTranslate2-based, 4x faster than vanilla Whisper, the standard choice). WhisperX for word-level timestamps (overkill for voice assistant).
- Models :`tiny` (39M),`base` (74M),`small` (244M),`medium` (769M),`large-v3` (1.5B). Bigger = more accurate, slower.
- Cost on GPU :`small` transcribes a 5-second utterance in ~100-300ms on a modest GPU.`medium` ~300-600ms.
- Cost on CPU :`base` ~500ms-1s for a short utterance on a decent CPU;`tiny` faster but less accurate.
- The accuracy/latency knob : for home commands,`base` or`small` is plenty (command vocabulary is small and predictable). For dictation or unusual names,`medium` +.
See the dedicated comparison: whisper-self-hosted-vs-faster-whisper-vs-whisperx-for-transcription.
### Stage 4: intent / LLM (optional - Llama / Qwen, or HA intent matching)
What to do with the transcribed text. Two paths:
#### Path A: HA intent matching (no LLM)
Home Assistant’s built-in Assist matches the text against intents (“turn on {entity}”, “what’s the {sensor}”). Deterministic, instant, no LLM. Handles the vast majority of home commands. This is the right default.
#### Path B: local LLM (conversational)
Route the text to a local LLM (Llama 3.x, Qwen 2.5/3, etc. via Ollama) for open-ended conversation, summarization, or complex multi-step requests. HA’s “conversation agent” can use Ollama as a backend.
- Cost : a 7-8B model on a GPU responds in 1-3 seconds for a short answer. On CPU, 5-15 seconds - usually too slow for voice.
- The trade : vastly more capable (“should I bring a jacket?” reasoning over weather data) but adds the most latency of any stage.
- Tool-calling : modern HA + Ollama supports the LLM calling HA services (turn on lights AND explain why), blending Path A and B.
For LLM runtime choice: ollama-vs-localai-vs-lm-studio-vs-llamafile-vs-vllm. For securing the Ollama endpoint: securing-self-hosted-ollama-with-an-auth-proxy.
