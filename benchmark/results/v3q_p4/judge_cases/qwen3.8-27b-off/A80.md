ASSISTANT: So at full 32-bit precision, the weights alone come out to about 261 gigabytes. Drop down to 4 bits and you're at roughly 33 gigabytes for the weights, and at 2 bits it's about 16 gigabytes. To be clear, those figures cover just the model weights; in practice you'd also need room for activations, the KV cache during generation, and whatever overhead your runtime adds, so real memory use will be somewhat higher than these numbers.

The trade-offs are worth understanding because they're not free. The core idea is that you round each weight to the nearest value representable with your limited bits, and that rounding introduces error. At 4 bits you can only distinguish sixteen distinct values per weight instead of billions, so every weight is an approximation of its original. In practice, modern quantization methods like GPTQ or AWQ do this cleverly enough that a 4-bit model typically loses only a small amount of quality on most tasks, which is why 4-bit has become the standard for running large models on consumer hardware.

Going to 2 bits is where things get much rougher. With only four representable values per weight, you're throwing away a lot more information, and the degradation becomes genuinely noticeable. You'll see more hallucinations, weaker reasoning, and poorer performance on nuanced tasks. Some research has shown 2-bit can work with very careful calibration and specialized techniques, but it's at the edge of what's practical for a model this size.

There are a few other costs beyond accuracy. Quantized models often need special kernels to run efficiently, so not every hardware setup benefits equally. And if you ever want to fine-tune the model afterward, quantization makes that harder because you're working with a compressed representation rather than the original weights. The general rule of thumb is that 4-bit is a good balance for most people, while 2-bit is a last resort when memory is truly tight and you can tolerate a meaningful quality hit.
