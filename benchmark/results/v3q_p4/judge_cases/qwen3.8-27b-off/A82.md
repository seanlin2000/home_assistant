An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

- Must respect security constraints

## Design Principles
MCP is built on several key design principles that inform its architecture and implementation: 1. Servers should be extremely easy to build - Host applications handle complex orchestration responsibilities
- Servers focus on specific, well-defined capabilities
2. Servers should be highly composable - Each server provides focused functionality in isolation
- Multiple servers can be combined seamlessly
3. Servers should not be able to read the whole conversation, nor “see into” other servers - Servers receive only necessary contextual information
- Each server maintains isolation
- Cross-server interactions are controlled by the host
4. Features can be added to servers and clients progressively - Core protocol provides minimal required functionality
- Servers and clients evolve independently
## Capability Negotiation
The Model Context Protocol uses a capability-based negotiation system where clients and servers declare their supported features on each request. Clients include their capabilities in`_meta.io.modelcontextprotocol/clientCapabilities` on every request. Servers advertise their capabilities in response to `server/discover`, which clients may call before any other request for up-front capability discovery.
- Servers declare capabilities like tool support, resource subscriptions, and prompt templates
- Implemented server features must be advertised in the server’s capabilities
- Receiving resource update notifications requires opening a
`subscriptions/listen` stream with the desired resource URIs
- Tool invocation requires the server to declare tool capabilities

## What Are MCP Tools?
MCP Tools are functions or services that an AI model can use to perform real-world actions. These actions usually involve doing something outside the AI system, such as calling an API, updating a database, or sending a message.

MCP Resources are data sources that the AI model can access to read information. These are typically read-only and provide context or knowledge to the AI.
## What Are MCP Prompts?
MCP Prompts are structured instructions or templates that guide how the AI model should think, behave, and respond.

ASSISTANT: Here's how I'd draw those lines, then the architecture.

An API is a general contract between two programs: one side says "here's what I can do and here's the shape of my requests," and the other side speaks that language over HTTP or similar. It's model-agnostic — it doesn't know or care whether a human, a script, or an LLM is on the other end. A REST endpoint for weather is an API whether you call it from a phone app or a chatbot.

A software tool is narrower in spirit: it's a single, self-contained capability that does one job — fetch this URL, run this query, convert these units. It has inputs, outputs, and side effects, but no idea who's driving it. In the LLM world, "tool" usually means a function with a JSON schema that a model can decide to call.

An MCP server is a packaging and discovery layer built specifically for LLMs. It's an open standard — JSON-RPC based — where one process exposes three kinds of primitives: tools (actions the model can take), resources (read-only data it can pull into context, addressed by URI), and prompts (reusable templates). The host application — your app, Claude Desktop, Cursor, whatever — connects to the server, calls a "list" method to discover what's available, and then invokes things with a "call" method. The key value is composition: you write the server once and any MCP-compatible host can plug it in, and each server stays isolated so one bad dependency doesn't leak into another.

So the relationship is roughly this: an API is the wire protocol between programs; a tool is one capability; an MCP server is a standardized container that advertises a bundle of tools (plus resources and prompts) to LLM hosts. An MCP server will often wrap ordinary APIs under its tools — for example, a web-search MCP server is mostly calling a search API on the model's behalf.

Now, your local-LLM web research system. I'd split it into four layers:

The host, or orchestrator. This is your application. It runs an MCP client that connects to one or more servers, discovers their tools, and — this is the part people forget — actually runs the model in a loop: send the user's question plus the available tool schemas, let the model emit a tool call, execute it, feed the result back, repeat until the model produces a final answer. A local LLM like one running under Ollama or llama.cpp doesn't do this loop by itself; your host code does.

The model layer. Your local LLM, ideally served with function-calling support — Ollama and vLLM both expose OpenAI-style tool-call endpoints, which makes the orchestration straightforward. Pick a model that reliably emits valid JSON for tool calls; smaller models get flaky here.
