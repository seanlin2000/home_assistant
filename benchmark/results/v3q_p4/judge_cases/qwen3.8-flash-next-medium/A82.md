Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Let me take these three in order, because they're layers of the same stack rather than alternatives to each other.

An API is a contract between two pieces of software. It defines how you ask for something and what shape the answer comes back in — an endpoint, some parameters, a JSON response. A weather service exposing "GET /forecast?city=Portland" is an API. It's passive: it doesn't know or care that anyone is calling it, and a human programmer has to write the code that calls it.

A tool is an API plus the packaging that makes it callable by an agent. A tool has a name, a written description, and a typed parameter schema — and crucially that description is written in natural language, because the thing deciding whether to call it is a language model. In other words, an API becomes a tool when you attach instructions the model can read and reason about, plus a runtime that actually executes the call and feeds the result back into the model's context.

An MCP server is a specific, standardized way of exposing tools — Model Context Protocol, an open specification from Anthropic — so that one server can advertise its tools, and any MCP-speaking client or agent can discover them at runtime instead of having them hand-coded into one application. Think of MCP as USB-C for tools. Before it, every agent framework had its own bespoke plugin format, and a tool written for one framework was useless in another. An MCP server is just a process, usually local, that says "here are my tools, here are their schemas, call me over JSON-RPC." It can also expose resources and prompt templates, not just functions, but tools are what people mostly use it for.

So the hierarchy is roughly: an API is the capability, a tool is that capability described for a model to invoke, and MCP is the standard plumbing that lets tools be found and invoked across different clients.

For your local web-search-and-summarize system, here's how I'd build it in that studio, on a laptop-class machine.

The core insight is that summarization should happen outside the small model, not inside it. A local model with a few thousand tokens of usable context cannot read a fifteen-thousand-word page. So you don't give it "read webpage." You give it "search," and "extract," and let it orchestrate them.

Layer one is the model itself, served by something like Ollama, llama.cpp with llama-server, or vLLM, exposing an OpenAI-compatible endpoint and native function-calling or tool-calling capability. That last part matters more than raw size: a seven- or eight-billion-parameter model with a good tool-use template — Qwen or Llama class — will follow a search-then-read-then-answer loop reliably. A larger model with a poor tool template will hallucinate a search result instead of calling the tool.

Layer two is the tools, implemented as an MCP server you run locally. Three tools, deliberately coarse.

The first is search_web. It takes a query and a result count, calls a search API — Tavily and Brave Search both have generous free tiers, and an MCP server for either already exists — and returns a short list of titles, URLs, and one-line snippets. Keeping this output small is the whole point; the model spends context on the results list.

The second is fetch_page. It takes a URL, fetches it, and — this is the important engineering detail — strips HTML down to readable text, drops navigation, ads, scripts, and cookie banners, truncates to a sane character budget, and returns the remainder. This is where you'd use something like a readability extractor rather than dumping raw HTML into your model. A local proxy fetcher is nicer than an API-based reader service here, because it costs nothing and doesn't send your URLs to a third party, though an extraction API saves you the maintenance.

The third is summarize, and this is the part most people get wrong. Don't make the chat model summarize a long page inline. Run a second, smaller local model — a four-billion-parameter instruct model, or a dedicated summarization model like a BART or a small Qwen — as a separate endpoint, and have fetch_page pipe the cleaned text through it. So the tool the agent sees is "retrieve_and_summarize(url, focus)", and it returns a few hundred words plus a couple of verbatim quotes and the source URL. The big model then reasons over the summary, not the page.

Layer three is the agent loop: model receives the question, decides whether it needs the web at all, issues a search, judges whether the snippets answer it, fetches and summarizes the one or two URLs that look most authoritative, and synthesizes. Add three guardrails and it becomes dependable rather than flaky. A hard cap on tool calls per turn — say four — prevents a runaway loop. A "tool result goes to the model, not to me" rule, so a fetched page never appears verbatim in your output. And a rule you should really bake in: treat everything the fetcher returns as untrusted data, because a webpage can contain text that reads like instructions, and your tool loop must never execute it.

If you want the short version: an API is a capability with a formal contract, a tool is that capability annotated so a model can decide to use it, MCP is the standard for exposing those tools so any client can plug them in, and your system is a tool-calling local model, one small MCP server with three tools, and a second cheap model doing the heavy reading so your main model never has to hold a whole webpage in its head.
