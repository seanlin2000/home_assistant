Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

## Negotiation
Every request declares the protocol version it is using via the`io.modelcontextprotocol/protocolVersion` key in its `_meta` field, and the server accepts or rejects each request independently. On Streamable HTTP, the same value is also carried in the `MCP-Protocol-Version` header. Clients and servers MAYsupport multiple protocol versions simultaneously. If the server does not support the requested version, it responds with an
`UnsupportedProtocolVersionError` listing the versions it does support. The client can then retry the request with a mutually supported version, or surface an error to the user if none exists. Clients that want to select a version up front can call `server/discover`, a mandatory RPC that returns the server’s supported protocol versions, capabilities, and identity in a single request. Calling it is optional: a client is free to send any request directly and handle a version error if one comes back. For interoperability with servers and clients that implement the handshake-based protocol revisions (`2025-11-25` and earlier), see Backward Compatibility.

An API is just a contract: a defined way for one piece of software to talk to another. It could be an HTTP endpoint, a function in a library, or a command-line interface. APIs are aimed at programmers and other programs, and the consumer is assumed to already know how to use them from documentation.

A software tool is the concrete thing doing the work: a CLI program, a script, a library function. A tool is standalone, and it serves whoever is running it.

An MCP server is a specific kind of application built to the Model Context Protocol — a standard, now pretty much the industry default, for exposing capabilities to LLMs. An MCP server advertises a set of tools, each with a name, a plain-language description, and a JSON schema for its arguments, and clients discover them at runtime over JSON-RPC. So the relationship is: an MCP server is an app that wraps software tools, and those tools usually call ordinary APIs underneath. The whole point of the wrapping is that the interface is self-describing enough that a model can figure out how to use it without any human-written documentation. As of this year the spec moved to a stateless core over streamable HTTP, which matters for scaling but not for how you'd use it locally.

Now the architecture for your local LLM web setup. There are three layers.

Layer one is the model, say an eight or twelve billion parameter model served by Ollama or llama.cpp, one with decent function-calling support.

Layer two is the MCP server, a small Python or TypeScript app using the official SDK, exposing two or three tools. Tool one is web search: it takes a query, calls a search provider — Tavily, Brave, or the DuckDuckGo endpoint — and returns a handful of titles, URLs, and snippets. Tool two is page fetch: it takes a URL, downloads it, converts the HTML to readable text with something like trafilatura, and truncates it. You might add a third tool for pagination or re-reading a saved page if you adopt the newer spec's explicit-handle pattern, where a tool returns an identifier and the model threads it back on later calls.

Layer three is a thin orchestrator that runs the agent loop: it sends the user's question plus the tool descriptions to the model, the model emits a tool call, the orchestrator executes it through the MCP server, feeds the result back, and repeats until the model answers.
