The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. # Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: The short version is this: the model itself never leaves your machine, but whatever it decides to put into a search query does. So the real question is not whether your data goes out, but what ends up in that query string.

Let me walk through the three buckets.

What stays local. The model weights stay on your hardware. Your full conversation history stays local. Any files or documents you fed the model stay local. The model's reasoning, its drafts, and its final answer all get generated locally. And critically, anything you typed that the model does *not* extract into a search query never leaves. If you paste a private email into the chat and the model just talks to you about it without searching, the provider never sees a word of it.

What gets transmitted. By default, a web-search tool sends the query string it was asked to run, plus the normal plumbing of an API call: your API key in the authentication header, a user-agent, a timestamp, and your IP address. That IP is important and easy to underestimate — it tells the provider roughly where you are and, combined with a timestamp, ties the request to you.

The subtle risk is the query itself. This is where most data leakage actually happens. If you ask the model to summarize your lease agreement, or help you write an email about a medical issue, the model will often build a search query out of the specific details it read. So your private content can get partially echoed back out into a query, even though the original document never moved. The provider would then see that query — and whether they keep it depends on their logging and retention policy, which varies a lot from provider to provider. That's the one fact I'd want you to check directly against the specific service you're using, because I can't speak for any one of them. There's also a structural nuance worth verifying: some wrapper tools send just the query, but a few "smart search" plugins send more context along with it. Read your particular tool's documentation to confirm it's the minimal kind.

How to minimize exposure, roughly in order of impact. First, control the query. Put an instruction in your system prompt telling the model to redact, generalize, or remove names, dates, addresses, and any personal details before it forms a search, and to search only for the general concept it actually needs. Second, add a scrubbing layer between the model and the API — a small interceptor that strips patterns like emails, phone numbers, and names out of the outgoing query, or that simply blocks queries above a certain sensitivity. Third, hide the network identifiers. Route the API call through a proxy or VPN so the provider sees a neutral IP instead of yours, and use a dedicated, rotatable API key with the narrowest scope rather than a broad one. Fourth, pick or self-host the backend deliberately. If you can run your own search aggregator, you own the logs and the traffic, which is the strongest version of this. If you use a hosted API, compare retention and "do you train on this" policies before committing. And finally, log every outgoing query on your side so you can actually see what the model is sending and catch anything it shouldn't.

If you tell me which search API and which local framework you're running, I can dig into the specifics of what that combination transmits and what its logging policy actually is.
