Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Start with the layer each one lives at.

An API is a contract between two programs. It says: send me this shape of request at this endpoint, I'll return this shape of response. It has no idea a language model is involved, and it doesn't care who calls it. The Wikipedia API, the Brave Search API, your bank's REST endpoints — all just well-defined doors.

A software tool is a piece of software that actually does a job. In the LLM world, "tool" has narrowed to mean something specific: a named function with a description and typed parameters, handed to the model so the model can decide to call it. So a tool is the unit of action the model can choose. The same underlying capability might be a shell script, a Python function, or a library call, but the moment you describe it to a model with a schema, it becomes a tool in the agent sense.

An MCP server is a way of publishing tools to models in a standard way. It's a server, usually speaking JSON-RPC over stdio or HTTP, that announces "here are my tools, here are their schemas" when a client connects, and the client can then call them. It also exposes two things beyond tools: resources, which are readable data like a file or a database table, and prompts, which are reusable templates. The value is that the wiring gets done once. Write an MCP server for your Postgres database and suddenly every MCP-capable client can use it, instead of you writing bespoke glue for each app. People compare it to USB-C for AI tooling, and the analogy is fair. An MCP server is very often just a thin wrapper around an API or a local tool, adding the model-facing description that a raw API lacks.

So the relationship is: an API is the underlying contract, a tool is the callable unit the model picks, and MCP is the distribution and discovery mechanism for getting tools in front of models. They aren't rivals.

Now for your system. I'd build it in layers, and I'd keep the MCP layer optional.

At the bottom, serve the local model with something that supports OpenAI-compatible function calling — Ollama, llama.cpp's server, or vLLM if you have the GPU headroom. Pick a model with genuinely good tool-calling, because that's where local models are weakest. Qwen's instruct line, Hermes, and Llama's recent tool-tuned variants are the usual picks. If the model can't reliably emit valid JSON tool calls, nothing above it works.

On top of that, an agent loop you control yourself: the model receives the tool schemas, emits a tool call, your runtime executes it, appends the result as a tool message, and re-prompts until the model produces a final answer or you hit a cap. Put a hard limit on iterations and total tokens, or small models will loop.

Then three tools, deliberately coarse. A search tool that takes a query and returns eight to ten results with title, URL, and a snippet. Self-host SearXNG if you want no third party, otherwise Brave or Tavily, both cheap. A fetch tool that takes a URL and returns the extracted main text, trimmed to something like four thousand characters, with a timeout and a real user agent. Use a readability-style extractor rather than raw HTML; feeding raw HTML to a local model with a small context window is the fastest way to destroy its reasoning. And a summarize tool that takes the fetched text and produces a compressed answer.

That last point is the real architecture decision, and it's where local systems usually fail. A local model often has eight to thirty-two thousand tokens of context. Do not dump a fetched page into the main conversation. Instead, run a separate call — possibly to a smaller, faster model — that maps over chunks of the page and reduces them into a summary, and return only the summary to the main agent. Your main loop then reasons over summaries, not pages. It costs you extra calls, but it keeps the context clean, which matters far more for small models than for frontier ones.

Two supporting pieces. Cache fetched pages on disk, keyed by URL, so re-runs don't re-fetch. And keep a small local vector store over pages you've already summarized, so a repeat question can skip straight to retrieval.

Should you make the search and fetch tools an MCP server? If your only consumer is your own single app, no — plain function calling is less machinery, and MCP adds a process boundary and a protocol you have to debug. If you want the same tools available to Claude Desktop, to other clients, and to teammates, then wrap them as an MCP server and keep your agent loop as a thin client on top. In my experience the sensible move is to write the tools as ordinary functions first, then expose them through MCP, since the wrapping is easy once the functions are solid.

One honest caveat about the whole design: tool-calling is where local models are weakest, and the biggest quality gap in this kind of system isn't the search or the summarization, it's the model picking the right tool with the right arguments. Keep the tool set to three or four, make the descriptions boringly explicit, validate every call with a schema library like Pydantic, and retry a malformed call once with the validation error fed back.
