The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. ASSISTANT: The short version: your model weights and your conversation stay on your machine, but everything the model decides to look up is effectively a message you typed into a search company.

Here's the boundary in detail.

What stays local. The model itself, its weights, your chat history, your system prompt, any files the agent reads on your disk, and the intermediate reasoning tokens. None of that is transmitted unless the software explicitly puts it into a tool call. That last clause is the important one, because the tool call is where the leakage happens.

What actually goes out over the network. The API call itself carries the query string, which the model usually synthesizes from your prompt rather than you typing it. So if you paste in a draft contract and the model decides to search for "termination clause enforceability in Delaware commercial leases 2024," that phrasing — possibly including names, deal terms, or an unusual detail that identifies you — arrives at the provider as plain text. Along with it go your API key and account identity, which links every query to you as a billable customer, plus your IP address, the request timestamp, and usually a user agent or client identifier. Many agent frameworks also send a snippet of surrounding context so the provider can pick better results, and some managed setups, like Azure's Grounding with Bing tools, are designed around the provider seeing a fairly large slice of the request rather than a short query string.

Then there's the return leg, which people forget. If your agent calls an extraction or reader endpoint, or fetches the URLs the search returned, you're also telling that provider which pages you read. And several search APIs marketed as independent are aggregators that forward your query to a bigger index. Tavily's own privacy policy says that when its index can't answer, your query is shared with third-party search index providers, so a query can travel further than the company you signed up with.

Retention is the part that varies most, and it changes often, so treat this as a snapshot rather than a guarantee. Brave markets a zero-data-retention option and runs its own index of tens of billions of pages, but its API terms describe retaining query records for up to 90 days for billing and troubleshooting, so you'd want to confirm the plan you're actually on. SerpApi caches each search with an identifier so you can re-fetch it, and offers a Zero Trace parameter to skip storing search parameters and metadata if your account supports it. Those opt-outs exist, but they're not the default.

Now, minimizing exposure, roughly in order of impact.

Add a rewriting layer between the model and the search API. Have a small step that turns the model's intent into a generic, impersonal query, stripping names, emails, addresses, amounts, account numbers, and anything oddly specific. This is the single biggest win, because it addresses the leak at its source.

Use a search-only identity. A separate email, a separate payment method, and a dedicated API key that isn't tied to your main account. Prefer a plan with contractual query non-retention, and turn off any logging or query history dashboard retention you can find.

Route from a box that isn't yours. A cheap VPS or a proxy you control, so the provider sees that IP rather than your home IP. Combined with the separate account, this makes the queries hard to attribute to you personally.

Keep the request narrow. Don't let the framework ship your whole conversation as context. Cache results locally so repeated questions don't re-hit the API. Cache aggressively and your total number of exposures drops a lot.

Consider self-hosted search instead. SearxNG on your own server, or your own crawler with a local index, means the query goes to infrastructure you own. The tradeoff is real: you inherit rate limits, bot detection, staleness, and the maintenance, and the results are usually worse than a commercial index.

A firewall allowlist to the single API host is worth doing too, since agent frameworks fetch more URLs than you'd expect.

One risk worth flagging that has nothing to do with the search provider. Prompt injection through search results is the main way a local model's private data gets taken. A page you never intended to read can contain text that tells the model to search for something it shouldn't, and the provider then learns your secret on your model's behalf. Search only results from domains you allow, treat fetched page content as untrusted data rather than instructions, and don't let the agent chain search calls without a limit.

I'd put honest uncertainty on the specifics: retention periods and account-level options on all of these providers shift, and marketing pages and legal terms don't always agree — Brave's zero-retention claim and its 90-day billing retention language are a good example. Before you commit to a provider, read the terms of service rather than the landing page.
