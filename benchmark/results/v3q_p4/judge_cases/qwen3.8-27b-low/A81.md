Reference sketch (what a correct answer must contain):
The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. Websites the assistant then fetches see the IP address and the requests. What stays local: the audio and transcription if speech is processed locally, the full conversation and history, the model's reasoning and answers, and anything never put into a query. Minimizing exposure: keep personal details out of queries (write queries from the question, not the whole conversation), search only when needed, cache results, use a privacy-focused provider or a self-hosted metasearch proxy such as SearXNG, route through a VPN for IP privacy, and check the provider's data-retention terms.

# Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: This is a good question to think through carefully because the answer depends on exactly how your local setup is wired, but the general picture is pretty clear.

**What stays on your machine.** Your model weights, your full conversation history, your local files, and all the inference computation. The LLM formulates a search query entirely on your side, and it processes the results it gets back locally. The search provider never sees any of that directly.

**What actually crosses the wire to the search API.** The minimum is the search query string itself, plus standard HTTP metadata: your IP address, the request timestamp, your user-agent string, and your API key or bearer token, which identifies your account to them. Depending on the provider, they may also record the user-agent and referer header. Some conversational search APIs accept optional context or conversation-ID parameters, and if you pass those, the provider gets that text too. The response they send back is search results: titles, snippets, and URLs, which then flow into your local model.

**What the provider can infer from all that.** They know exactly what you searched for, which reveals your research topic and, if you're careless, specific personal details. They know your approximate location from your IP. They can build a timeline of your queries over time. They know you as a user tied to an API key. They do *not* see your full conversation, your system prompt, your local documents, or anything else your LLM is working with.

**How to minimize what they see.** The most important thing is controlling the query itself. Write a system prompt that instructs your local model to generate short, minimal, generic search queries, and to strip out any names, addresses, or identifiers before sending. You can also add a small local pre-processing step that redacts sensitive strings from the query before it hits the API. Choose a provider with an explicit no-logging or short-retention policy; some, like DuckDuckGo's API or certain open endpoints, are more privacy-conscious than the big cloud search APIs. If your use case allows, route the request through a local proxy or a simple tunneling service so the provider sees a different IP, though that adds latency. Keep the API key in a dedicated account separate from your personal one, so even if they keep logs, they're tied to a burner identity. And if you're working on something genuinely sensitive, consider replacing the external API entirely with a local search index over your own documents, or a self-hosted search backend, so nothing leaves your machine at all.

The short version: the search provider sees the query and the network metadata, nothing more. The main risk is that a well-formed natural-language query leaks more about you than you intended, so the single highest-leverage fix is making your local model produce minimal, de-identified queries.
