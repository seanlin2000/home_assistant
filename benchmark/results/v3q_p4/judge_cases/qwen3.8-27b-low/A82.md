Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Let me walk through each concept, then sketch the architecture.

An API is the broadest term. It's any contract that lets one piece of software talk to another — an HTTP endpoint that returns JSON, a gRPC method, a function you import from a library. The web search service you'd hit, the database you'd query, the model you'd send a prompt to — all of those are accessed through APIs in one form or another. The word just means "here's a defined way for me to ask this thing to do something and get something back."

A software tool, in the LLM context, is a specific function the model is allowed to call. When an LLM "uses a tool," it means the model produces a structured request — usually a function name plus arguments — and your application runs the actual code and hands the result back. The tool is the thing that does the work: it's the function that hits the search API, the function that downloads a page, the function that compresses text into a summary. Tools are what the model sees and decides to invoke.

An MCP server is a packaging and transport layer for tools. The Model Context Protocol, introduced by Anthropic and now widely adopted, standardizes how you expose tools, resources, and prompts to any MCP-compatible client. Under the hood it's JSON-RPC over stdio or HTTP, and the client — the thing running the LLM conversation — discovers what tools the server offers, asks the model which one to call, forwards the call, and returns the result. The value is that you write the MCP server once and any compliant client can plug into it. Without MCP, every client has its own proprietary way of registering and calling tools, and you'd have to write a different adapter for each.

So the relationship is: a tool is the unit of work, an API is how the tool talks to the outside world, and an MCP server is the standardized envelope that lets a model client discover and invoke those tools without custom wiring.

Now, the architecture for your use case.

You'd have three layers. The first layer is the local LLM, running through something like Ollama, llama.cpp, or vLLM. It produces the reasoning and the tool-call decisions. The second layer is the MCP server, which you'd write in Python or TypeScript using the official SDK. Inside that server you'd register three tools: one for web search, one for fetching a page, and one for summarization.

The search tool would call an external search API — SearXNG running locally if you want privacy, or a hosted provider like Tavily or Serper if you don't mind a key. It takes a query string, returns a list of results with titles, URLs, and snippets.

The fetch tool takes a URL, downloads the page with a real HTTP client, strips the HTML to text — something like the readability or trafilatura libraries do a nice job of this — and returns the cleaned text, truncated to a length that fits the model's context window.

The summarization tool is interesting because you have two options. The cheap option is extractive: score sentences by term frequency or use a small dedicated model and return the top sentences. The richer option is to call back into your local LLM with a "summarize this" system prompt and pass in the fetched text. That second option is what I'd pick, because your local model is already there and it gives you a much better summary. You just need to be careful about context length — if the fetched text is longer than your model can handle, you'd chunk it and do a map-reduce: summarize each chunk, then summarize the summaries.

The third layer is the client application that glues it all together. You'd use an MCP-compatible client — the Python SDK has a client library, and if you're running the model through Ollama or a similar runtime, there are ready-made MCP client integrations. The client connects to your MCP server over stdio, tells the model what tools are available, runs the conversation loop, and when the model emits a tool call, the client forwards it to the server, gets the result, and feeds it back to the model. The model can then decide whether it has enough to answer or needs to call another tool — maybe it searches, reads one page, decides it needs a second page, and so on.

A few practical notes. Run the MCP server as a separate process from the LLM runtime, connected over stdio, so a crash in one doesn't take down the other. Keep your tool descriptions crisp and specific in the MCP server's tool definitions, because that's what the model reads when deciding whether to call the tool — vague descriptions lead to the model calling the wrong tool or not calling any. And cap the text you feed back from fetch and summarize to something the model can actually work with; a 128-token window for a search snippet and maybe two to four thousand tokens for a fetched page is a reasonable starting point, depending on your model's context size.

The whole thing ends up being: local LLM, a small MCP server process with three tools, and a client loop that shuttles messages between them. You could probably write a working version of it in an afternoon.
