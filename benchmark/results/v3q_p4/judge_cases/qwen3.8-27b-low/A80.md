USER: What does it mean to quantize a 70-billion-parameter language model to 4-bit or 2-bit precision? How much memory would the weights require in each case, and what trade-offs does quantization introduce?

ASSISTANT: Quantization is the process of taking the model's weights, which are normally stored as 16-bit floating point numbers, and rounding them to a smaller number of bits. Think of it like reducing the color depth of an image. A full-color photo has millions of possible shades per pixel; a 4-bit image has only sixteen. You lose some detail, but the file gets much smaller, and for many purposes the result looks close enough.

Concretely, a 70-billion-parameter model stores 70 billion weight values. In 16-bit floating point, that is 70 billion times 2 bytes, or 140 gigabytes of memory just for the weights. At 4-bit, each weight takes only half a byte, so you get 35 gigabytes. At 2-bit, each weight takes a quarter byte, giving you 17.5 gigabytes. Those are the weight-only figures; real inference also needs memory for the key-value cache and activations, which add on top, but the weights dominate.

The trade-offs are worth understanding. The first is quality. Going from 16 bits to 4 bits means each weight is snapped to one of only 16 levels instead of 65,000. In practice, 4-bit quantization is widely considered a good deal. Models at 4-bit typically lose only a small fraction of their quality on standard benchmarks, and the loss is often below what different models of the same size show from one another. Going to 2 bits is much more aggressive. You are snapping each weight to one of only four levels, and quality degrades noticeably, especially on tasks that require precise reasoning like mathematics, code generation, and following complex instructions. Some research has shown 2-bit can still be usable for simpler tasks, but it is a much riskier bet.

The second trade-off is speed, and it is a little counterintuitive. You might expect fewer bits to mean faster, and in many cases it does, because the bottleneck in inference is often memory bandwidth rather than compute. Moving 35 gigabytes through memory is faster than moving 140. However, the hardware must dequantize the weights back to higher precision before doing the actual arithmetic, and that step adds overhead. The net effect is usually positive, especially on consumer hardware where memory bandwidth is the real constraint.

The third trade-off is calibration. Good quantization is not just naively rounding each weight. Methods like GPTQ, AWQ, and the GGUF formats used by llama.cpp use a calibration set of representative inputs to figure out the best mapping from 16-bit values down to fewer bits, minimizing the total error across the model. If the calibration set does not match the kind of text you will actually feed the model, the quality loss can be worse than expected.

So in summary: 4-bit gives you about a four-fold memory reduction with modest quality loss, and is the sweet spot for most people who want to run a 70-billion model on a single high-end GPU or a modest multi-GPU setup. 2-bit gives you an eight-fold reduction but at a real quality cost, and is more of a research or extreme-constraint scenario.
