Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Great question, and the honest answer is that these three terms sit at different layers of abstraction, which is why people mix them up.

An API is the most general concept. It's just an interface that one piece of software exposes to another, a contract saying "if you send me this request in this format, I'll give you this response." A web API using HTTP and JSON is the most common kind, but APIs can be function calls inside a process, database queries, command-line interfaces, you name it. An API doesn't care who's calling it or why. It's a capability with a defined shape.

A software tool is broader still and vaguer. A tool is anything that does work for you: a command-line program, a library, a script, a service. An API is often *how* you access a tool, but the tool is the thing doing the work. So an API is an interface, a tool is an instrument, and a single tool might be reachable through several different interfaces.

An MCP server sits on top of this. MCP, the Model Context Protocol, is a standardized way to expose tools to a large language model. Under the hood, an MCP server is usually just a regular program that wraps existing APIs or commands and re-exposes them through MCP's conventions: it advertises a list of tools with their names, descriptions, and input schemas, and when the model decides to call one, the server executes it and returns a result. So the MCP server is a kind of adapter or translator. It takes ordinary capabilities and packages them so that *any* MCP-compatible model client can discover and use them without you writing custom integration code for each model.

Now the architecture for your use case. You want a local LLM that can search the web, fetch pages, and summarize them. I'd structure it in four layers.

First, the model layer. You'd run the LLM locally, say through a server that exposes an OpenAI-compatible API, which gives you an inference endpoint you can talk to. The model needs to support tool calling or function calling, because that's the mechanism that lets it decide *when* to search versus when to answer from what it already has.

Second, the MCP server layer. You'd build or install an MCP server that exposes three tools: a web search tool, a fetch tool, and possibly a summarize helper. The search tool would call some search API or a search engine. The fetch tool would take a URL, pull the page, and convert the HTML into clean text, because feeding raw markup to a local model is wasteful and noisy. If you want, a third tool could do pre-summarization or truncation, though you'll usually just let the model summarize. The key design choice here is keeping the tools narrow and their descriptions precise, because the model is reading those descriptions to decide what to do. A well-written tool description does more for reliability than any amount of prompt engineering.

Third, the orchestration layer, sometimes called the agent loop. This is the glue. It sends the user's question to the model, and when the model responds with a tool call, it hands that call to the MCP server, gets the result, and feeds the result back to the model. The model then either calls another tool, for instance searches, then fetches, then answers, or it produces a final natural-language response. You keep looping until the model stops requesting tools. This loop is the heart of the system, and you want to add sensible limits on it, a maximum number of tool calls, timeouts on fetches, so a confused model doesn't loop forever or hang on a slow website.

Fourth, a few practical safeguards. You'd want to clean and chunk fetched content so it fits the local model's context window, since local models tend to have smaller context than the big cloud ones. You'd rate-limit or cache your search calls if you're hitting a paid API. And you'd decide how much you trust the fetched content, because the model will read webpages and can be manipulated by text on them, so the prompt should frame retrieved content as data to be summarized, not instructions to follow.

The nice thing about choosing MCP specifically is portability. Because the tools are exposed through a standard, the same search-and-fetch server works with whatever local model you swap in later, and the same model can pick up entirely different MCP servers for other capabilities. You're not welding your integrations to one framework.
