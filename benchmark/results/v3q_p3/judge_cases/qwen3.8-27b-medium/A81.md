Reference sketch (what a correct answer must contain):
The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. Websites the assistant then fetches see the IP address and the requests. What stays local: the audio and transcription if speech is processed locally, the full conversation and history, the model's reasoning and answers, and anything never put into a query. Minimizing exposure: keep personal details out of queries (write queries from the question, not the whole conversation), search only when needed, cache results, use a privacy-focused provider or a self-hosted metasearch proxy such as SearXNG, route through a VPN for IP privacy, and check the provider's data-retention terms.

# Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: The short version is that your model, your conversation, and anything you keep in local files stay on your machine, but the search provider sees the exact query you send it plus the network metadata that comes with any web request. Here's how I'd sort it out.

What stays local is everything about the model and the conversation around it. The weights themselves, the full prompt you gave it, the model's step-by-step reasoning, the intermediate text it generates, and any documents you loaded in from your own disk. None of that crosses the wire just because you're doing a search.

What gets transmitted is narrower than people worry about, but it's the part that matters. When your agent (or you) sends a search request, the provider receives the query text exactly as written, your IP address and so your approximate region and ISP, a timestamp, and whatever headers go along with the request like a User-Agent string or an API key. Then it hands the results back to you, which is fine. The thing to internalize is that the provider sees the query, not the conversation that produced it. It doesn't see your prompt or the model's internal reasoning unless you deliberately copy that content into the query.

That last point is where real exposure creeps in. If your conversation contains something sensitive and the query is built from it, the sensitive bit rides along in the query string. "Look up the dosage for John's condition" sends both the name and the condition to a third party, even though the provider never saw the rest of your discussion. So the leak is precisely what you choose to put in the query, plus the IP and timing metadata attached to it.

One more nuance worth stating plainly: HTTPS protects you from eavesdroppers on the network between you and the search service, but it does not hide the query from the search provider itself, because the provider is the endpoint. Encryption in transit is table stakes, not privacy from the destination.

To minimize exposure, the highest-leverage move is to sanitize the query before it leaves the machine. Strip names, exact identifiers, and precise personal values, and substitute neutral phrasing or placeholders so the provider gets a generic version of what you need. Keep the model's private reasoning local and only emit the minimal query that will actually answer the question. On the request side, use a clean or generic User-Agent, don't attach identifying custom headers, and check the provider's policy on whether it logs queries and whether it uses them for training, since that determines how long your queries linger. If tying your IP to the searches matters, routing through a VPN or an intermediate proxy breaks that link, though remember the provider still sees the query words. Finally, if recency matters less than privacy, a fully local search over your own index, or a local search tool, removes the transmission step entirely, at the cost of coverage and freshness.

So the mental model is: the boundary of what leaks is the query plus standard request metadata, and most of your risk comes from being careless about what you put in that query rather than from the architecture itself.
