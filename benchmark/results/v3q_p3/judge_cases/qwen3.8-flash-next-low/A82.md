# Question A82 (category A)
What it tests: Software architecture for tool use
Expected search behavior: no
Expected reply: an ordinary answer

Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

ASSISTANT: Three different things that get mixed together because they overlap in practice.

An API is a contract between pieces of software. It says: here is an endpoint, here is the shape of the request, here is the shape of the response, here is how you authenticate. It is designed for a programmer to call. Brave Search has an API, OpenWeatherMap has an API. Nothing about an API assumes an AI is involved, and nothing about it tells a machine *when* it would be useful to call.

A tool is a unit of callable capability that an agent can *choose* to invoke, described in a form the model itself can read: a name, a natural-language description of what it does and when to use it, and a typed parameter schema. The tool is the abstraction the model reasons over. A tool can wrap an API — "web_search(query)" calling Brave's API is one obvious case — but a tool doesn't have to touch the network at all. "Rename this file" is a tool. So the relationship is: APIs are how software talks to software; tools are how software presents capabilities to a model for it to select. A tool is usually a thin, model-facing wrapper over an API or a local function, plus the description and schema that make it selectable.

An MCP server — the Model Context Protocol — is the plumbing that turns APIs and local functions into a self-describing tool catalog any AI application can use. It's an open, JSON-RPC based client-server protocol. A server exposes three kinds of things: tools, which are callable functions with schemas; resources, which are URI-addressed data you can read rather than invoke, like a file or a database table; and prompts, reusable templates. It runs either over stdio for a local process or over a streamable HTTP transport for a remote one, and it handles discovery, so the client can ask "what can you do?" before asking the model to decide. The current spec revision is dated 2026-07-28, with beta SDKs in Python, TypeScript, Go and C#. The point of MCP isn't that it's a better way to call a function — it's that you build the connector once per external system and every MCP-compatible client can then use it, instead of writing bespoke function-calling glue for each model and each app.

Now your system. You want four layers.

The model layer. The non-negotiable requirement is a model with real tool calling. A model that can only generate prose cannot drive an agent loop; you'd have to fake it with fragile text parsing. So the model must emit structured tool calls in a format the runtime can parse and parse back into the conversation. In Ollama, check that the model reports a "tools" capability before you do anything else — recent versions reject a request containing tools with an HTTP 400 if the model can't handle them, which is a hard failure rather than the silent "it just ignored my tools" behavior people describe. Llama 3.3 and similar open models do have reliable function calling, but the chat template has to be applied exactly as specified, and outputs should be validated against your schema with a retry.

The orchestration layer. This is the loop, and it's the piece people forget. Model returns a tool call, the runtime executes it, the tool result is appended to the conversation, the model runs again, and you repeat until the model produces a final answer instead of another call. You need a cap on the number of rounds and a token budget, because tool definitions alone can eat an absurd amount of context — one documented example is around 3,900 tokens for 25 Playwright MCP tool definitions, against a 4,096-token default window on smaller setups.

The tool layer. I'd build three tools. First, `web_search`, which takes a query and returns a short list of title, URL and snippet. Three different things that get mixed together because they overlap in practice.

An API is a contract between pieces of software. It says: here is an endpoint, here is the shape of the request, here is the shape of the response, here is how you authenticate. It is designed for a programmer to call. Brave Search has an API, OpenWeatherMap has an API. Nothing about an API assumes an AI is involved, and nothing about it tells a machine *when* it would be useful to call.

A tool is a unit of callable capability that an agent can *choose* to invoke, described in a form the model itself can read: a name, a natural-language description of what it does and when to use it, and a typed parameter schema. The tool is the abstraction the model reasons over. A tool can wrap an API — "web_search(query)" calling Brave's API is one obvious case — but a tool doesn't have to touch the network at all. "Rename this file" is a tool.
