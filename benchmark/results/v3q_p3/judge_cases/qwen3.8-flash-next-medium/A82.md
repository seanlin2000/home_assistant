Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Sure. These three things overlap a lot, so it helps to think of them as three different layers of the same stack.

An API is a contract between pieces of software. It says: send me a request shaped like this, and I'll give you a response shaped like that. It's designed to be called by programs, it's deterministic, and the calling program decides when to call it. A REST endpoint that returns JSON for a weather query is an API. Nothing about an API assumes there's a model involved anywhere.

A software tool, in the agent sense, is a capability packaged for a model to choose. It has a name, a description written in plain language, and a parameter schema. What makes it a "tool" rather than just a function is that the LLM decides whether and when to call it, based on the description you gave it. The model emits a structured call, your code executes it, and the result comes back as a message the model can read. So a tool is an API plus a description plus a decision-maker that happens to be a language model.

An MCP server is a standardized way to ship tools to models. MCP, the Model Context Protocol, is an open protocol Anthropic released in late 2024 and since opened up. Instead of writing custom function-calling glue for every client, you run a small process that speaks MCP over JSON-RPC, usually on stdio for local servers or over HTTP for remote ones, and it advertises its tools, its resources, and reusable prompt templates. Any MCP-capable client, Claude Desktop, LM Studio, various coding agents, picks those tools up automatically. So the relationship is: an API is the underlying contract, a tool is what you expose to a model, and an MCP server is the distribution mechanism that gets those tools into whatever client you're using. An MCP server usually wraps an API. It isn't a replacement for one.

For your local LLM system, I'd build it in four layers.

First, the model host. Run a local model with actual function-calling support through something like Ollama, llama.cpp, LM Studio, or vLLM, exposed through an OpenAI-compatible endpoint. Not every local model handles tool calling well, so pick one that does, something in the Qwen or Llama lineage with a tool-use variant, and test it on simple calls before trusting it with a multi-step task.

Second, the tools themselves. Three of them. A search tool taking a query plus optional count and recency, calling something like Brave Search, Tavily, or Serper, and returning titles, URLs, and short snippets. A fetch tool taking a URL, doing an HTTP GET, running readability extraction, converting HTML to plain text or markdown, and returning the cleaned body. And optionally a chunking or extraction tool, because raw pages are far longer than you want in a local model's context window.

Third, the plumbing. You have a choice here. If this is one script you control, plain function-calling in an agent loop is simpler, and you should skip MCP entirely. If you want those same tools available in multiple clients, or you want to reuse third-party MCP servers like the official Fetch or Filesystem ones, wrap your tools in an MCP server. A local stdio MCP server is a good middle ground: the tools live in their own process, so a crash or a bad page fetch doesn't take down your agent, and you can swap clients later without rewriting anything.

Fourth, the loop and the guardrails. The agent sends the user's question plus tool schemas, the model picks a tool, you validate the arguments against the schema, execute with a timeout, truncate the result to a token budget, and feed it back, repeating until the model produces an answer. For summarization specifically, I'd avoid dumping whole pages into the main model. Either truncate to a few thousand characters per page, or run a smaller local model in a map-reduce step: one extractive summary per page, then the main model synthesizes across pages and attributes claims to sources.

Two things people skip and then regret. Untrusted web content is a prompt-injection vector, so treat fetched text as data, strip anything that looks like instructions, and never let it trigger a tool call. And log every call: query, URL, tokens in and out, so you can tell when the model hallucinated a source versus actually read one.

A rough budget: a 14B to 32B quantized model on a 16 to 24 gigabyte GPU handles this comfortably, with a small 3B model doing the per-page extraction. If you tell me what hardware you've got, I can be more specific about model sizes and context limits.
