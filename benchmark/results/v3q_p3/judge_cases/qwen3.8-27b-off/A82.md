Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

#### Understanding the Discovery Exchange
The`_meta` fields and the discovery response together serve several purposes: 1. Protocol Version Selection : The`io.modelcontextprotocol/protocolVersion` field declares the version the client is speaking on this request, and`supportedVersions` in the response lists the versions the server accepts. If a server does not support the requested version, it rejects the request with an`UnsupportedProtocolVersionError` listing the versions it does support, and the client retries with a mutually supported version. 2. Capability Discovery : The client declares its capabilities in`io.modelcontextprotocol/clientCapabilities` on every request, and the server returns its own`capabilities` object from`server/discover` . This tells each party which primitives the other can handle (tools, resources, prompts) and whether change notifications are available, so unsupported operations are never attempted. 3. Identity Exchange : The`io.modelcontextprotocol/clientInfo` field in the request’s`_meta` and the`io.modelcontextprotocol/serverInfo` field in the result’s`_meta` provide identification and versioning information for debugging and compatibility purposes.

## The three concepts

An **API** is a general-purpose contract between two pieces of software. It says "here are the operations you can call, here's what you send, here's what comes back." A web search API, a payments API, a weather API — all APIs. They're designed for *programs* to talk to other programs, and they assume the caller knows exactly what it wants.

A **software tool** is vaguer and more informal. It usually means a self-contained program or function that does one job — a calculator, a scraper, a file converter. A tool doesn't necessarily expose an API; it just *does* something when you run it. In the LLM world, "tool" also has a specific meaning: a function you describe to the model in a structured way (name, description, input schema) so the model can decide to call it.

An **MCP server** sits between those two. It's not itself an API or a tool — it's a *standardized wrapper* that exposes tools, data, and prompts to LLM applications through a common protocol. Think of it as an adapter: your underlying capability (an API, a database, a local script) gets wrapped in MCP so that *any* MCP-compatible client can discover and use it without custom integration code.

The key distinction: an API is the raw interface, a tool is the unit of work, and an MCP server is the *standardized way to package and advertise* those tools so AI agents can find and call them. One MCP server can expose many tools; one tool might be backed by an API or just local code.

## Architecting your local LLM web-search system

Here's how I'd structure it, from bottom up:

**Layer 1 — The raw capabilities.** You need three building blocks:
- A **web search function**. Either call a search API (Brave, Tavily, SerpAPI) or run a local search engine. This returns a list of URLs with titles and snippets.
- A **page-fetching function**. Given a URL, retrieve the content. For robustness, strip HTML to clean text — something like `trafilatura` or `readability` in Python, or a headless browser for JavaScript-heavy pages.
- A **summarization step**, which is just your local LLM itself, prompted to condense the retrieved text.

**Layer 2 — Wrap them as an MCP server.** This is where the architecture gets interesting. You'd write a small MCP server (Python or TypeScript SDK) that exposes two tools:
- `web_search(query)` → returns ranked results with URLs and snippets.
- `fetch_page(url)` → returns the cleaned text content of that page
