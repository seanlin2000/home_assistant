Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Let me separate the three terms, because they're often conflated but they're at different layers.

An API is a contract. It's the definition of what a piece of software can do and how another piece of software is allowed to ask it to do it — usually a set of endpoints or functions with typed inputs and outputs, spoken over some transport like HTTP, gRPC, or a local function call. An API has no body of its own; it's a boundary. A weather service, a Stripe payment, and a database driver all have APIs, but the API is the interface, not the thing doing the work.

A software tool is the program that actually does the work — the script, the CLI, the library, the daemon. A tool might expose an API, or it might not at all. A shell script that scrapes a page has no API in any formal sense, but it's absolutely a tool. So the relationship is: a tool is the implementation, an API is the interface it (optionally) exposes.

An MCP server sits on top of that. The Model Context Protocol is an open standard, originally from Anthropic, for connecting AI models to external capabilities. An MCP server is a program that speaks that protocol. It advertises a list of tools — each with a name, a human-readable description, and a JSON Schema for its parameters — plus optional "resources" and "prompts." Any MCP client (an app, an IDE, an agent framework) can discover those tools, let the model decide which to call, forward the structured call to the server, and hand the result back to the model. So an MCP server is a specific, standardized way of packaging tools so that many different AI clients can share them without custom glue code per client.

Now for your system. You want a local LLM — something running through Ollama, llama.cpp, or LM Studio — to search the web, fetch pages, and summarize. I'd break it into four parts.

The first part is the model itself. Any local model that reliably emits structured tool calls will do; smaller models are finicky about it, so you want something that handles function calling cleanly.

The second part is an orchestration loop. The model doesn't execute anything on its own. You need a thin piece of code — a wrapper script, or a framework like LangChain or LlamaIndex if you don't want to hand-roll it — that does this: send the user's question to the model, the model responds with a tool call like "search the web for X," your code runs that search, appends the result to the conversation, and asks the model again. The model might then call fetch_url on the most promising link, get the content back, and finally produce a natural-language summary as its answer. That loop — model proposes, you execute, you feed back, repeat until it gives a final answer — is the heart of it.

The third part is where the actual capabilities live, and this is where your API-versus-MCP question lands in practice. I'd expose at least two tools, not three. Tool one is web search, which calls some search backend — Brave Search API, SerpAPI, Tavily, or a self-hosted SearXNG if you want it fully local — and returns a list of titles, URLs, and snippets. Tool two is fetch URL, which pulls a page, strips the boilerplate with a content extractor like trafilatura or a readability algorithm, and returns the main text truncated to a fixed token budget. That truncation matters a lot: without it, a single Wikipedia page can blow your context window and tank the model's ability to reason about the answer.

I would deliberately not make summarization a tool. The model is the best summarizer you have in the stack, and the natural final step of the loop is the model reading the fetched content and writing the summary in its own response. Building a "summarize" tool would mean having the model call itself through a round trip, which is clunky and just adds a failure point. If you ever do want a pre-summarization pass — say, for very long documents where you need to compress before the main model even sees them — that's a separate, smaller model call in the pipeline, not a tool the main model invokes.

The fourth part, which is easy to skip and regret, is hardening. If the model picks the URLs, it can be talked into fetching localhost addresses or internal network endpoints, so you want a basic allowlist or a check that blocks private and loopback IP ranges. You also want timeouts
