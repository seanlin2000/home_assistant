Reference sketch (what a correct answer must contain):
The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. Websites the assistant then fetches see the IP address and the requests. What stays local: the audio and transcription if speech is processed locally, the full conversation and history, the model's reasoning and answers, and anything never put into a query. Minimizing exposure: keep personal details out of queries (write queries from the question, not the whole conversation), search only when needed, cache results, use a privacy-focused provider or a self-hosted metasearch proxy such as SearXNG, route through a VPN for IP privacy, and check the provider's data-retention terms.

# Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: This is a good question to think through carefully because the answer is more nuanced than people usually expect.

So here's the basic architecture. Your language model runs entirely on your machine — the model weights, the conversation you're having with it, the system prompt, any reasoning it does, and the text it generates all of that stays on your hardware. None of that touches the search provider.

What does get sent to the search API is the query string you build and send. That's the critical piece. If your local model decides it needs to look something up, it formulates a search query, and that text — plus a few bits of metadata — is what the provider sees. The metadata typically includes your IP address, a timestamp, your user-agent string, and your API key, which identifies your account. If the API supports location-based filtering or time-range parameters, those travel along too. And from a network perspective, the DNS lookup and the TLS handshake reveal which domain you're connecting to, even if the content is encrypted in transit.

What the search provider does not see is your full conversation, your system prompt, the model's intermediate reasoning, your local files, or anything else the model has in its context window. The only window into your session is the query text itself.

So the practical risk is this: the query is a summary, but it can be a revealing one. If you ask your local model something like "what's the prognosis for the condition my mother was diagnosed with last month, given the medication she's on," and the model sends that whole sentence as a search query, the provider now knows a fair amount about a specific person in your life. The model doesn't have to be malicious or sloppy to do this; it just tries to construct a query that will return useful results, and sometimes the most useful query includes a lot of context.

To minimize exposure, there are a few layers. First, and most important, sanitize the query before it leaves your machine. You can do this in the code that bridges your local model to the API. Strip out names, specific medical details, addresses, and anything that identifies a person or your personal situation. A good rule of thumb is to send the query you'd be comfortable typing into a public search bar. Second, cache results locally so you're not re-sending the same query every time. Third, pick a search API whose data-retention policy you can actually read and that you trust. Some providers log queries for a period; others don't. Fourth, you can route the request through a local proxy that strips or anonymizes headers, though that's more about metadata than content. And finally, if your use case is sensitive enough, consider whether a local search index or a search tool that runs entirely offline would be sufficient, even if it's less current than a live API.

The short version: your model, your conversation, and your reasoning stay home. The search query is the one thing that crosses the wire, so treat it like the sensitive artifact it is.
