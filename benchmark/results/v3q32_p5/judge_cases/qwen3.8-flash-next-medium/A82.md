Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: An API is a contract: a defined way for software to expose capabilities over a network, typically endpoints that take structured requests and return structured responses. A software tool is any program or function an agent can invoke to do a concrete job, like fetching a URL or running a search query. An MCP server is a specific standard for packaging those tools so an AI client can discover and call them uniformly, handling connection, listing available tools, and routing calls, rather than each agent writing bespoke integrations.

For a local LLM with web abilities, I'd build it in layers. First, a search API client, a tool wrapping something like Serper or Bing, returning ranked titles and URLs. Second, a retrieval tool that fetches a URL and strips HTML to readable text, keeping output bounded to fit context. Third, a summarizer, either the local model itself running over the retrieved text, or a small local model for speed.

I'd wrap the search and fetch tools in a single MCP server, so the local model, through a runner like Ollama's tool support or a LiteLLM proxy, can see them, decide when to search, pick which pages to read, and then summarize. Add a cache to avoid re-fetching, and caps on results and token length to keep the local model's context manageable.
