# Exchange 1

USER: Imagine I want to build a private, locally hosted voice assistant that can answer general questions, search the web, control smart-home devices, and have natural conversations. I have a $1,000 hardware budget. Propose an architecture, explain the components, identify the biggest limitations, and prioritize what I should build first.

ASSISTANT: Here's a sensible build.

**Architecture, as a pipeline.** A wake-word listener runs constantly on the CPU — openWakeWord or similar — so nothing leaves your machine until you say the trigger phrase. Speech-to-text via Whisper or its faster local variant converts your question to text. An orchestration layer routes intent: chitchat and general questions go to a local language model, usually a 7–10B quantized model served by Ollama or llama.cpp; factual lookups trigger a small search tool that hits the web and feeds results back to the model; smart-home commands become a JSON tool call to Home Assistant, which already speaks every device protocol you'd care about. Text-to-speech closes the loop — Piper is lightweight and local.

**Where the budget goes.** Roughly $400–500 on a used RTX 3090, since VRAM is the whole game for response speed; $150 for a motherboard, PSU and RAM to hang it off; $100 on a decent USB microphone array plus a small speaker; the rest on a Pi or mini-PC running Home Assistant and the always-on wake listener.

**Biggest limitations, honestly stated.** Small local models are unreliable at multi-step reasoning and prone to confidently wrong answers, which is exactly why the search tool matters. Function calling on 7B models is brittle — smart-home control works because the commands are short and schema-constrained. You get no multimodal help, no image understanding. Latency is the other tax: wake, transcribe, generate, speak is easily 2–4 seconds on consumer hardware, so interruptions and barge-in are hard. And Whisper with no GPU or with a tiny one degrades badly in a noisy apartment.

**Build order.** First: Home Assistant plus wake word plus a hard-coded intent list — lights, thermostat, no language model at all. That alone is a useful product in a weekend and proves the audio path. Second: add a local LLM for conversation, so you learn how your hardware behaves under generation load. Third: web search as a tool, because it needs the model to call tools well. Fourth: TTS polish and conversation memory.

The reason for that order is risk. Voice control of a lamp is a solved problem; a local model that reliably decides to search, then summarizes, is where your project will actually spend its debugging time.
