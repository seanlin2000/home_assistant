Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: An API is a general interface—just a set of functions other software can call, like a weather service or a search engine. A tool is any small program or function you wire into an LLM to do one job, like fetching a page or calling that API. An MCP server is a standard package of tools plus instructions, spoken in a common protocol, so the LLM framework can discover and use them without custom code.

To give a local model web access, I'd build two or three small MCP tools: one that calls a search API, one that fetches and strips a page down to text, and one that hands the text to the model for summarization. Your local app, something like Ollama behind a framework, talks to the MCP server, which talks to the web. Each step stays simple and swappable.
