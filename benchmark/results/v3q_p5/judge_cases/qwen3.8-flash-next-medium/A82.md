Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

ASSISTANT: Here's the cleanest way to separate the three, because they're often conflated.

**An API is a contract for a service.** It's a documented way for one program to ask another program to do something or hand over data, with defined endpoints, request shapes, and responses. The OpenWeather API, Stripe, a search provider like Brave or Serper, a REST endpoint on your own machine. The key point: an API knows nothing about language models. It has no idea a model is calling it. It's a general-purpose interface, designed for programmers.

**A software tool, in the agent sense, is a capability wrapped so a model can choose to use it.** It has a name, a natural-language description that a model can read and reason about, and a parameter schema the model must fill in. A tool is usually a thin shell around something else, often an API, sometimes a local function, a shell command, or a database query. What makes it a tool is not the implementation underneath; it's that it's exposed inside the model's context, the model emits a structured call saying "use this tool with these arguments," and the result comes back into the conversation as an observation. So a tool is an API plus a description, a schema, and a place in the model's decision loop. You can also have tools that are not APIs at all, like "run this Python snippet" or "write a file."

**An MCP server is a program that publishes tools, resources, and prompts over a standard protocol**, so any MCP-speaking client or host application can discover and call them without bespoke glue code. It's the USB-C of agent integration. Messages are JSON-RPC, over stdio for local servers or Streamable HTTP for remote ones. The current spec is the 2026-07-28 revision, which is a fairly big change: the protocol is now stateless request/response rather than a persistent bidirectional session, each request carries its own version and capability metadata, and features like roots, sampling and logging were deprecated in favor of tool parameters and resource URIs. MCP also draws a useful line that most homebrew tool systems blur: tools are model-controlled, the model discovers and invokes them, while resources are application-controlled context that the host decides to pull in, and prompts are user-controlled templates.

The relationship in one sentence: an API is the underlying service, a tool is that service packaged for a model to invoke, and MCP is a standard transport and discovery protocol for shipping tools from a server to whatever client is hosting the model. MCP is not a replacement for tools. An MCP server's main job is usually to expose tools.

Now for your system. Given a local model, I'd build it in layers, and I'd be honest about one thing up front: MCP is optional here. If this is just for you on one machine, plain function calling in a Python loop is simpler and I'd start there. MCP earns its keep when you want those same web tools reusable across several clients, or when you want to reuse existing community servers instead of writing your own.

Layer one, the model and its serving stack. Ollama is the easiest path, llama.cpp's llama-server gives you more control, vLLM if you're serving multiple users. What matters is picking a model that is genuinely good at tool calling, not just good at prose. In 2026 the commonly recommended picks for local agent loops are Qwen 3.6, including the 35B-A3B mixture-of-experts variant which fits about 16 gigabytes of VRAM, and Gemma 4 27B for a 24-gigabyte machine, with Llama 3.3 70B cited as the most reliable well-formed caller if your hardware fits it. I'd treat those as directional recommendations from published tests rather than absolutes, and I'd validate with your own loop before committing.

Layer two, the agent harness. This is the loop, and it's where most of the real engineering is. It sends the user question plus tool definitions to the model, the model either answers or emits a tool call, your harness executes it, appends the result, and iterates until the model produces a final answer. Put hard caps: a maximum of six to eight tool calls per question, a timeout per call, and a maximum total tokens of fetched content in context. Small local models are the ones most likely to loop forever, so the guardrails are not optional.

Layer three, the tools, and I'd keep them to three with deliberately narrow contracts. A search tool that takes a query plus optional recency and returns a small structured list of title, URL, snippet, and published date, nothing more. A retrieval tool that takes a URL, fetches it, converts HTML to clean text or markdown, strips boilerplate, truncates to a few thousand words, and returns it along with the final URL and fetch status. A third tool worth adding that people forget: fetch and return a specific section, or re-fetch with a max length, so the model can go back for detail instead of dragging a whole page around in context. Good tool descriptions matter more with local models than with frontier ones, because they have less capacity to infer what you meant.

Layer four, if you want MCP. Wrap those same three functions in one MCP server using the Python or TypeScript SDK, and expose search and fetch as tools, plus maybe a resources entry for cached pages. Run it as a local stdio server, or bind a local HTTP server to 127.0.0.1 and check the Origin header. Then your harness is just an MCP client, and you can point Open WebUI, LM Studio, Cline, or your own script at the same server. The bridge from Ollama's tools API to MCP is a small amount of glue, or you can use an existing bridge tool. I'd also say this: if you want a real browser for JavaScript-heavy pages, the puppeteer MCP reference server exists and is widely used in local tool-calling benchmarks, but it's a much heavier dependency than an HTTP fetch plus readability extraction.

Layer five, summarization. Don't ask the model to summarize a page it read in one pass in a single long context window if you can avoid it. For short pages, one pass is fine. For long ones, chunk the retrieved text, have the model extract facts from each chunk with a fixed output shape, then do a final synthesis pass over just the extracted facts. This gives you grounded summaries that survive long documents, and it keeps the loop's context small.

Layer six, the two things that actually break in production. First, security. Treat every fetched page as untrusted data and never as instructions, because prompt injection through a webpage is the classic way a retrieval agent gets hijacked. In the fetch tool, block localhost and private IP ranges, enforce a short timeout, cap redirect counts, cap response size, and prefer a search provider you've contracted with over scraping Google. Second, cost and rate limits, since search APIs are the one part that isn't local and will bill you.

If you want the shortest version: model plus harness, three narrowly scoped tools, fetch content sanitized into plain text, summarization as a separate grounded pass, and MCP only once you want those tools shared across more than one client.

Here's the cleanest way to separate the three, because they're often conflated.

**An API is a contract for a service.** It's a documented way for one program to ask another program to do something or hand over data, with defined endpoints, request shapes, and responses. The OpenWeather API, Stripe, a search provider like Brave or Serper, a REST endpoint on your own machine. The key point: an API knows nothing about language models. It has no idea a model is calling it. It's a general-purpose interface, designed for programmers.

**A software tool, in the agent sense, is a capability wrapped so a model can choose to use it.** It has a name, a natural-language description that a model can read and reason about, and a parameter schema the model must fill in. A tool is usually a thin shell around something else, often an API, sometimes a local function, a shell command, or a database query. What makes it a tool is not the implementation underneath; it's that it's exposed inside the model's context, the model emits a structured call saying "use this tool with these arguments," and the result comes back into the conversation as an observation.
