## The problem with scrapers and Big Tech API options

Today, thousands of AI applications rely on Web search to ground responses to their user queries and to supply real-time data. This includes popular AI applications like chatbots and agents, as well as website-native search apps and more. With a search API, an end-user’s query is sent to a search engine via an API call. The search engine supplies grounded, relevant results, which are then served back to the user. A search API for the Web thus becomes one of the most critical components in an app’s technical stack.

Outside of Brave, other search APIs on the market today fall into one of two categories, both of which make ZDR impossible for them to offer:

### The scraper API

These supposedly “independent” search APIs aren’t independent at all, but instead scrape their results from Google or Bing. This reliance on Big Tech creates a few key problems:

- The data funnel : Most often, when your application sends a query to a scraper-based API, that API then sends the query to the Big Tech search engine in real-time. This means the search engine, which has its own extensive data collection and retention policies, will receive and log the original user query.
- Privacy blind spots : Even if the scraper-based API promises ZDR on their end, they’re still submitting user queries to a Big Tech search engine, which means ZDR cannot be maintained throughout.
- Enforceability : Scraper-based APIs will have no ability to enforce data deletion or data protection on the receiving Big Tech search engine.

With scraper-dependent APIs, a user’s query and data are shared with third parties without their knowledge, and with no recourse to have data deleted or removed. This is a practice the user would likely not consent to, and that can expose the app provider to compliance risk.

### The Big Tech API

While it may seem “better” to directly call the originating index, this strategy also presents problems. First, Big Tech companies like Google and Bing have closed their APIs, giving access either for a very small number of queries—too few to reliably build on—or not at all. This is particularly true since Bing formally retired its Search API.

Furthermore, Big Tech has given users few reasons to trust them. Big Tech’s entire business model is predicated on profiling users, with core infrastructure designed to track, store, and build profiles based on user queries, clicks, and behavior. So true ZDR is not an option.

## Brave’s independent architecture enables true ZDR

The Brave Search API offers a fundamentally different, simpler path to ZDR because of its unique, vertically integrated architecture: Brave is independent of Big Tech because it is powered by its own unique index of the Web. With the Brave Search API, no scrapers ever touch a customer’s queries or data.

### An independent index, no scrapers required

The foundation of the Brave Search API is the Brave Search index, a proprietary index of more than 35 billion webpages, with tens of millions of new pages crawled and updated each day. This index is built, maintained, and owned entirely by Brave.

When your application sends a query to the Brave Search API, the query is processed by Brave’s own index and ranking algorithms, which makes Brave’s architecture simple to visualize:

Without scrapers, Brave can ensure API customers retain control of their user data. Brave controls the entire search stack, from the crawling bot to the API endpoint, which allows easy enforcement of restrictive data retention policies. We can easily implement system-wide policies that prevent the logging or long-term retention of end-user search queries, or the use of those queries for unintended purposes. It also means we can offer true ZDR.

ASSISTANT: Good question, and the short version is this: running the model locally protects your *conversation*, not your *queries*. The moment your agent makes a search call, you're publishing whatever text ends up in that query, plus enough account metadata to tie it to you.

Here's the split. What stays on your machine: the model weights, your prompt and conversation history, any local files or notes you feed it, and any intermediate reasoning the model does that you don't send out. What leaves: the query string, which is the whole ballgame. That string is usually generated by your model *from* your prompt, so sensitive content can leak sideways into it. If you paste in a doctor's note or a contract and the model decides the right query is "symptoms described in a cardiology follow-up for someone named so-and-so," that phrasing is now a search query at someone else's data center. Beyond the query itself, the provider sees your API key, which maps to your account, which maps to the name, email, and payment details you signed up with, and your IP address plus request timestamps and volume. Some providers' per-request usage logs, like Tavily's, record queries against your key, and Tavily's own docs say they collect your query data and any documents you upload to the platform. Note the last part: search APIs increasingly offer extract, crawl, and deep-research endpoints, and those send entire URLs or documents to the provider for processing, which is a much bigger disclosure than a keyword query.

There's also a chain problem worth knowing about. Many search APIs marketed as independent are scraper-based, meaning they forward your query in real time to Google or Bing to get results. Brave argues in its own materials that this is the main privacy failure mode: even if the scraper vendor promises no retention on their end, Google or Bing receives and logs the original query, and the vendor has no way to enforce deletion. Brave claims to be the only search API with true zero data retention because it runs its own index of around 35 billion pages rather than scraping, with ZDR available on custom enterprise plans. Their privacy notice says they don't collect identifiers linking a query to an individual or device. Treat all of that as contractual claims you're taking on trust, not something you can verify from your side, which is exactly why the retention terms in a data processing addendum matter more than a blog post.

For minimizing exposure, the highest-leverage step is query hygiene: constrain the query-generation step so your model writes a neutral four-to-eight word query with no proper nouns, no numbers that look like account or claim IDs, no email addresses, no health or financial specifics. Paraphrase what you need instead of letting the model quote you. Assume every query will be read by a stranger. Second, prefer an independent-index provider over a scraper, and if your data is regulated or genuinely sensitive, ask for zero retention in writing rather than assuming a privacy badge means it. Third, self-hosting is the strongest option available to an individual: SearXNG is a free metasearch engine you can run in Docker on a cheap VPS, with a JSON API for agents, no account and no API key, and docs saying users are neither tracked nor profiled. The honest caveat is that self-hosting relocates trust rather than removing it, because SearXNG still forwards your query to whichever engines you enable, so configure it to use only Brave, DuckDuckGo, Mojeek or similar, and not Google or Bing. A middle path is an egress proxy you control: it strips or normalizes the user agent, keeps no logs, applies a rate limit, and can route through a network path that isn't your home IP, so your queries and your identity sit on different infrastructure.

Beyond that, keep the account itself low-information, which costs almost nothing: a separate provider account with a burner email and a card alias, one API key per workload so no single key accumulates a readable picture of your interests, keys rotated, spend caps set, and the key redacted from any local logs you do keep. Keep a local log of what you actually sent, because you can't minimize what you didn't measure. And reduce the number of queries that ever leave: keep a local index of the material you consult often, using embeddings plus keyword search, with a local result cache so the same question doesn't re-query the network. HTTPS protects the query from eavesdroppers on the path; it does nothing about the provider's own logging, which is the actual risk here.
