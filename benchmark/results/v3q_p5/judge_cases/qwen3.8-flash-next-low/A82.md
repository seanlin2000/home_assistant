Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

ASSISTANT: Here's the cleanest way to separate the three, because they live at different layers.

An API is a contract between pieces of software. It says: send a request shaped like this to this address, and you'll get a response shaped like that. It's called by code that a programmer wrote, and the caller's intent is fixed in the code. The Brave Search API, a weather service, or the OpenAI-compatible chat endpoint your own local inference server exposes are all APIs. Nothing about an API is specific to language models.

A tool is the model-facing version of that idea: a named function with a declared parameter schema that you offer to the model, and the model itself decides whether and when to call it, with what arguments. That's the key difference — a tool is model-controlled. A tool is usually implemented as a thin wrapper that eventually calls an API, or runs some local computation, but the defining feature is that the decision to invoke it belongs to the model, made mid-conversation rather than hardcoded in advance. A tool is a concept in an agent loop, not a network protocol, and every framework names and wires these slightly differently.

An MCP server is a process that speaks the Model Context Protocol, an open JSON-RPC based standard for exactly this wiring problem. It advertises three kinds of things: tools, which the model invokes; resources, which are passive data the host application chooses to pull into context; and prompts, which are templates the user explicitly invokes. Transports are stdio for local processes or HTTP for remote ones, with capability negotiation and OAuth for auth. So the relationship is: an API is the underlying capability, a tool is the button the model can press, and MCP is the standard socket that lets any host plug in any vendor's buttons without bespoke glue. One MCP server might wrap three APIs and expose five tools. The protocol also distinguishes control: tools are model-controlled, resources are application-driven, prompts are user-controlled, and the host is supposed to get explicit user consent before invoking a tool. Worth knowing that MCP is still moving: the current specification revision, 2026-07-28, actually dropped protocol-level sessions and the initialization handshake in favor of stateless requests with discovery, while 2025-11-25 is the recent stable one, so pin a version in a real deployment.

For your system, I'd build four layers.

First, inference. Run a local model behind a server that supports function calling — llama.cpp's llama-server, Ollama, LM Studio (which has had MCP support since 0.3.17), or vLLM. Model choice matters more than anything else here: you want a recent model explicitly trained for tool use, because a model that fumbles the JSON call format will make the whole system look broken. Qwen-class, Llama-class, or Gemma-class models in the range your hardware can hold.

Second, an agent loop that is the MCP client and the only thing that executes anything. It holds the conversation, asks the server for its tool list, passes those schemas to the model, executes whichever call the model asks for, feeds the result back as a tool message, and repeats until the model produces an answer. Keep a turn limit, an allowlist of permitted tools, and a log of every call.

Third, the MCP server, and here the design decision that matters most is the shape of the tools. Don't build one giant "get information" tool. Build a search tool that takes a query plus a count and a recency filter and returns only titles, URLs, and short snippets — deliberately small. Build a separate fetch tool that takes a URL and returns cleaned markdown, boilerplate stripped, capped at a few thousand words. The common failure mode in MCP servers is exposing huge raw documents as tool results, which floods the context window and wrecks latency. Keep results narrow and let the model chain search then fetch.
