Reference sketch (what a correct answer must contain):
GPUs run thousands of simple cores in parallel with dedicated matrix units and very high memory bandwidth (HBM), and neural networks are mostly matrix multiplication; token-by-token generation is largely limited by memory bandwidth. NVIDIA's software stack (CUDA) is a large part of the advantage. An ASIC is a chip built for one kind of job (Google's TPU), more efficient but less flexible. Specialized inference processors go further for serving models, for example large on-chip SRAM instead of external memory (Groq), wafer-scale chips (Cerebras), or chips hard-wired for transformers (Etched). A specialized chip can win when the model architecture is stable and matches the chip, when the workload is high-volume and fixed, when latency per token matters most, or on cost or power per token; it loses when models change, when flexibility or training matters, or where software support is thin.

## What Is Etched AI and the Sohu Chip
Etched AI is a chip startup founded in 2022, having raised roughly $800 million across four rounds, including a reported $500M round at a $5B valuation. Their first product is the Sohu chip, a transformer-only ASIC designed for autoregressive language model inference. The name and funding are real. The core architectural claim is that by implementing transformer attention as fixed-function silicon rather than as programmable matrix multiply instructions, Sohu can achieve throughput figures that no GPU can match for the same workload class. NVIDIA GPUs are programmable compute units that run CUDA kernels written in software. Groq's LPU is a dataflow processor with a custom compiler. Sohu takes a different position: there is no programmability layer at all. The chip does one thing, and it does it by being physically built for that one thing.
This is different from other custom inference chips in an important way. The Groq 3 LPU has a compiler that can, in principle, be extended. AMD GPUs support ROCm. Tenstorrent ships TT-Metal as open-source software. Sohu's architecture does not have a software abstraction layer in the same sense. If transformer attention changes in the next generation of models, the chip cannot adapt. For hyperscaler-built ASICs (Trainium 3, Maia 200, Meta MTIA), see the hyperscaler custom AI chip roundup.
## Sohu Architecture: The Transformer-Only Bet
### Fixed-Function Transformer Units
Transformer attention requires three core operations at each layer: computing query, key, and value projections; running multi-head attention across the KV cache; and passing results through a feed-forward network. On a GPU, each of these is a CUDA kernel that can be swapped out for a different implementation. PagedAttention, FlashAttention-2, and FlashAttention-3 are all software optimizations that improve how attention is computed on general-purpose hardware.
On Sohu, these operations are hardwired as static circuits. The chip does not have a general matrix multiply unit that runs attention software. It has physical circuits that implement the attention computation directly. This removes all of the overhead from kernel launch latency, memory allocation, and scheduler decisions. It also means the chip cannot run any computation that does not map to transformer attention. There is no way to compile a convolution, an SSM scan, or a diffusion U-Net step onto Sohu because there are no programmable units to target.
### On-Chip Memory Design
Sohu's throughput advantage comes primarily from memory bandwidth. The bottleneck for autoregressive decode on GPUs is KV cache reads: each new token requires reading the full KV cache from HBM. The H100 SXM5 has 80 GB of HBM3 with 3.35 TB/s of bandwidth. Every token generation step is bounded by how fast the model can read those KV cache values.
According to Etched's published materials and industry reporting, Sohu uses 144GB of HBM3E per chip with approximately 1.8x the memory bandwidth of an H100 SXM5. Our HBM3e vs HBM4 vs HBM4e inference guide covers what that same HBM3E generation delivers on GPUs, so you can see how much of Sohu's bandwidth edge comes from the memory type versus the fixed-function architecture. That gives Sohu more memory capacity than an H100 (80GB) at roughly 1.8x the H100's 3.35 TB/s bandwidth, using the same HBM architecture that GPUs use rather than replacing it with on-chip SRAM. The Groq 3 LPU takes a fundamentally different route: 500 MB of on-chip SRAM per chip achieves 150 TB/s bandwidth but with very limited context window capacity. Sohu's throughput advantage over GPUs comes from architectural specialization of transformer attention patterns built on top of standard HBM3E, not from a SRAM-based design like Groq. Multi-chip configurations are still required for large model weights since even 144GB fills quickly with 70B+ parameter models at full precision.

ASSISTANT: The short answer is that GPUs are good at AI inference because inference is mostly a memory-bandwidth problem wrapped in a matrix-multiply problem, and GPUs happen to be strong at both while remaining programmable.

Start with what actually happens when a large model generates a token. Autoregressive decoding is tiny in compute and enormous in data movement: for every token you generate, you have to read the model's weights and the KV cache. A seventy-billion-parameter model at sixteen-bit precision is about one hundred and forty gigabytes of weights, and an H100 has roughly three point three five terabytes a second of HBM bandwidth. Dividing one by the other, as a bound, means a single H100 cannot stream out a single sequence faster than about twenty-four tokens a second. The compute units are mostly waiting. That is why the tensor cores' enormous flop counts barely matter for single-stream generation, and why memory is the wall.

What GPUs do well is turn that weakness into a throughput story. Because a GPU is a programmable mass of parallel matrix multipliers, you can batch many requests together and amortize one read of the weights across dozens or hundreds of sequences. The arithmetic intensity goes up, the flop units start earning their keep, and cost per token falls far below anything built for single-stream speed. NVIDIA claims on the order of fifteen hundred tokens a second on Llama 3 70B using eight-bit quantization and TensorRT-LLM, and several thousand on Blackwell. That is the real reason GPUs dominate: not peak speed on one request, but throughput per dollar at high batch, plus CUDA, vLLM, quantization kernels, paged attention and speculative decoding, all of which keep improving on hardware that is already deployed. That last part matters commercially. A new attention algorithm can be adopted on a GPU in weeks as a software kernel. On a hardwired chip, it may simply be impossible.

Now the three categories you asked about.

A GPU is a general-purpose parallel processor. You write kernels, it runs almost anything: transformers, diffusion U-Nets, convolutions, mixture-of-experts with dynamic routing, training and serving on the same stack. Its fixed-function parts are modest, mostly the tensor cores and, on newer parts, the NVLink fabric.

An ASIC burns the computation into the silicon. Some of these are general accelerators with fixed dataflow shapes, Google's TPU with its systolic arrays being the archetype, and AWS Trainium, Microsoft's Maia and Meta's MTIA follow the same pattern: less flexibility than a GPU, but better area and energy efficiency for the operations the designer expected, and they exist mainly to serve one company's own models at hyperscaler scale. At the extreme end is Etched's Sohu, which hardcodes transformer attention as static circuits. Etched claims a single eight-chip server reaches five hundred thousand tokens a second on Llama 70B, roughly sixty-two thousand per chip, against something like seven hundred on an H100 at batch size one. That number is real only in the sense that it follows from the architecture, and I want to be careful: as of now, no independent third-party benchmark of Sohu exists, and it has only just begun shipping racks. The price is explicit. Sohu runs transformer attention and nothing else. No vision encoders, no diffusion, and MoE with dynamic expert routing is a genuine problem because irregular memory access does not map onto fixed-function logic. It also kept standard HBM3E rather than eliminating the memory hop, so much of its advantage is specialization plus newer memory, not a new memory architecture.

The third category is what Groq, Cerebras and SambaNova actually build: specialized inference processors that attack the bandwidth wall directly by keeping weights on the chip. Groq's LPU uses only about five hundred megabytes of SRAM per chip, but a compiler schedules everything statically and deterministically, giving aggregate SRAM bandwidth on the order of a hundred and fifty terabytes a second, at the cost of limited model size and context. Cerebras goes the opposite way, with a wafer-scale engine holding around nine hundred thousand cores and forty-four gigabytes of on-chip SRAM, enough to hold large models without going off-chip at all. SambaNova's SN40L is a reconfigurable dataflow chip with tiers of SRAM, HBM and DDR, so one rack can serve many models, and it is the one people pick for on-premises deployment. In practice these chips do reach the headline speeds: Groq reports sub-hundred-millisecond time to first token and roughly four hundred tokens a second on a one-hundred-twenty-billion model, while Cerebras reports figures in the thousands, near three thousand on the same model. OpenAI signed a contract for hundreds of megawatts of Cerebras capacity in early 2026, which is the strongest signal that this is not a demo.

The short answer is that GPUs are good at AI inference because inference is mostly a memory-bandwidth problem wrapped in a matrix-multiply problem, and GPUs happen to be strong at both while remaining programmable.

Start with what actually happens when a large model generates a token. Autoregressive decoding is tiny in compute and enormous in data movement: for every token you generate, you have to read the model's weights and the KV cache. A seventy-billion-parameter model at sixteen-bit precision is about one hundred and forty gigabytes of weights, and an H100 has roughly three point three five terabytes a second of HBM bandwidth. Dividing one by the other, as a bound, means a single H100 cannot stream out a single sequence faster than about twenty-four tokens a second. The compute units are mostly waiting. That is why the tensor cores' enormous flop counts barely matter for single-stream generation, and why memory is the wall.

What GPUs do well is turn that weakness into a throughput story.
