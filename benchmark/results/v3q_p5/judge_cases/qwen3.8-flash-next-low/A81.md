Reference sketch (what a correct answer must contain):
The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. Websites the assistant then fetches see the IP address and the requests. What stays local: the audio and transcription if speech is processed locally, the full conversation and history, the model's reasoning and answers, and anything never put into a query. Minimizing exposure: keep personal details out of queries (write queries from the question, not the whole conversation), search only when needed, cache results, use a privacy-focused provider or a self-hosted metasearch proxy such as SearXNG, route through a VPN for IP privacy, and check the provider's data-retention terms.

ASSISTANT: Short version: the model staying on your machine protects your documents and your prompts, not your curiosity. The moment a tool call leaves your laptop, the search provider learns what you searched for, in the clear.

Here's the split. What stays local is everything you never send: your prompt, your chat history, your files, the model's weights and reasoning, and anything you keep out of the tool call. What leaves the machine is the query string itself, plus the API key, your public IP address, a timestamp, and request parameters like how many results you want, language, and country. Some providers also receive the URL you're asking them to read, if you use their extract, crawl, or "read this page" endpoints, which tells them not just what you looked for but what you intended to read. And because the query was written by your model on your behalf, it can smuggle out details you never meant to disclose. A model asked "what's the latest on the Henderson matter?" sends "Henderson" to somebody else's logging system. Client names, project names, ticket numbers, internal file paths, and email addresses all routinely end up in generated queries.

On the provider side, what actually gets retained varies a lot. Brave's API privacy notice, updated in early November 2026, says records of queries submitted through a customer's account are kept for up to ninety days for billing and troubleshooting, with a zero-data-retention option available to enterprise customers, and it states plainly that Brave can only tie a query to an API account, not to an identifiable end user. That's a reasonable posture, though note the caveat: a distinct pattern of queries plus an API key can still be fingerprinted. Tavily is SOC 2 certified and advertises zero data retention on its enterprise plans, but its own documentation treats zero query retention as something you switch on in account settings rather than a default, and it collects your name, email, and company details when you sign up. Tavily was acquired by the AI infrastructure firm Nebius in February 2026, with its data policies said to be unchanged. Google's Custom Search JSON API is real, but I could not find a clear published retention window for API queries in the pages I read, so treat that as unspecified rather than private. The old standalone Bing Search APIs no longer exist at all: Microsoft retired them on August 11, 2025, and now pushes developers toward "Grounding with Bing Search" inside Azure AI Foundry, priced around fourteen dollars per thousand grounding transactions, which is an agent feature rather than a raw search endpoint.

One structural point worth understanding: many "search APIs" are scrapers that forward your query to Google or Bing under the hood. Even if the middleman promises zero retention on its side, the query still landed on a Big Tech index, so the guarantee can't hold end to end. If the provider doesn't run its own index, ask what's behind it.

To reduce exposure, the highest-leverage step is to make the queries generic before they go out. Add a sanitizing pass, either a small local model or explicit rules, that rewrites the tool call into bare keywords with names, addresses, numbers, and internal identifiers stripped. Prefer asking "quarterly revenue outlook 2026 semiconductor" over "why is Acme's Q3 guidance in draft_memo.docx too optimistic." Next, choose a provider with a contractual data-processing agreement and a written zero-retention option, and actually enable it rather than assuming it's on. Use a separate billing account and email for the API key, so the query log is attached to a disposable identity rather than your name. Cache results locally so the same question doesn't leave your machine repeatedly, and request few results rather than a wide page of them. Route the request through your own small server instead of straight from your laptop, which hides your home IP, though it doesn't hide the query. Avoid the extract and crawl endpoints when a snippet is enough, since fetching a page is a second disclosure.

Finally, the fully private option exists but costs you effort. Run SearXNG on your own machine or a home server, which aggregates public engines without an account and logs only what you configure it to log, or lean on account-free APIs like Wikimedia's search API for reference questions. Neither gives you Google-quality results on everything, but neither hands your questions to a third party's retention policy either. And remember the risk flows both ways: whatever the provider returns is untrusted text about to enter your model's context, so keep fetched content fenced off from tool permissions, or a hostile page can steer your local agent into doing something you didn't ask for.
