Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: The cleanest way to think about these three is that they live at different levels of abstraction, and they overlap rather than compete.

An API is a general-purpose contract between two pieces of software. It says, "here are the endpoints, here's the method, here's the shape of the data in and out." That contract could be REST, GraphQL, gRPC, or even a plain function call into a library. An API knows nothing about who's calling it or why. A weather service, a Stripe account, a search engine, a database — all expose APIs. The API is the wire protocol and the vocabulary.

A software tool is a general unit of work. It's any program or function that does a thing — fetches a page, converts a file, runs a query. On its own a tool is just code. The term becomes specific only in the context of an LLM, where a "tool" is something the model can *choose to call* in order to take an action, and the model reasons about which tool to use based on what you ask it. So a tool is a capability the model can reach for.

An MCP server is a particular standardized wrapper that exposes tools, and also data and prompt templates, to LLMs. MCP is Anthropic's Model Context Protocol. An MCP server speaks JSON-RPC over a transport, and it advertises three kinds of things: tools (functions the model can invoke), resources (readable data, like a file or a page), and prompts (templated instructions). The big idea is that instead of every LLM app hard-coding its own glue to talk to a specific service, you write the service once as an MCP server, and any MCP-capable client — whether it's a desktop app, an IDE, or a local LLM harness — can pick it up. Under the hood, an MCP server is usually just doing the ordinary thing: it receives a tool call, makes an API request, cleans up the response, and sends it back. So an MCP server is a tool-exposing program that follows one protocol.

To sum the relationship up in one sentence: an API is how software talks to other software, a tool is a capability a model can invoke, and an MCP server is a standardized way to package tools up so any model can use them without custom wiring.

Now for your local LLM web agent. I'd break it into four parts.

First, the local model, running through something like Ollama or a local inference server. I'd pick a model that handles structured function calling well, because that's the weak point in a local setup. Small local models are often bad at emitting clean tool calls, and the whole design falls apart if the model can't reliably say "call search with this query." If your model is shaky at tool use, you can lean on a stricter JSON schema for the calls, or use a model that's known to be decent at it.

Second, an agent loop, the orchestrator or harness. This is the piece people forget. It's the program that runs the model, reads whatever tool call the model emits, actually executes it, shoves the result back in, and repeats until the model decides it has enough to answer.
