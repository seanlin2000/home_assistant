The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. # Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: When you run a local model and wire it to an external search API, the boundary is pretty clean, and the thing that crosses it is narrower than people usually expect.

**What stays on your machine:** the model weights, the full conversation history, the system prompt, the model's internal reasoning, the final generated answer, and any local files the model might read. None of that leaves your computer.

**What gets transmitted:** the search query string. Here's the subtle part — that query is something your local model *generates* based on the conversation, and it may contain fragments of what the user said. If someone tells the model "look up the filing deadline for my patent on a lithium battery anode," the model will send a query that includes "lithium battery anode patent filing deadline." The search provider sees that text, plus your IP address, your API key, and a timestamp. They also return results — snippets, URLs, sometimes full page content — which come back to your machine and get fed to the local model.

So the attack surface is: what the model decides to put in a query, and what that reveals about your conversation.

**How to minimize exposure:**

First, add a local pre-filter. Before any query goes out, strip it down to the bare minimum. You can have the model generate a query using only the terms it genuinely needs to search, rather than passing conversational context through. A simple rule: the query should be the shortest phrase that would find the right result.

Second, consider whether a self-hosted search layer is worth it. SearXNG, for instance, is a meta-search engine you can run on your own hardware. It hits multiple search backends, but the query never goes to a single third party under your identity. You trade some convenience for a lot more control.

Third, if you do use a hosted API, read the logging policy carefully. Some — like Brave Search API — state they don't store query logs. Others are less clear. This matters because the query text is the sensitive part, not just the fact that a search happened.

Fourth, consider routing through a proxy so the search provider sees a shared IP rather than yours, which decouples your identity from the query in their logs.

And one practical point: if your use case involves anything truly sensitive — health information, business secrets, legal matters — the safest option is to not search at all for those topics, or to search a manually sanitized, generic version of the question and do the sensitive reasoning locally. The model is local, so it can do that reasoning without needing the search provider to see it.
