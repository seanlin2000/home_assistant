Reference sketch (what a correct answer must contain):
GPUs run thousands of simple cores in parallel with dedicated matrix units and very high memory bandwidth (HBM), and neural networks are mostly matrix multiplication; token-by-token generation is largely limited by memory bandwidth. NVIDIA's software stack (CUDA) is a large part of the advantage. An ASIC is a chip built for one kind of job (Google's TPU), more efficient but less flexible. Specialized inference processors go further for serving models, for example large on-chip SRAM instead of external memory (Groq), wafer-scale chips (Cerebras), or chips hard-wired for transformers (Etched). A specialized chip can win when the model architecture is stable and matches the chip, when the workload is high-volume and fixed, when latency per token matters most, or on cost or power per token; it loses when models change, when flexibility or training matters, or where software support is thin.

## Memory Bound vs Compute Bound: What to Shop for
### When FP8 or Bigger Batches Change the Answer
FP8 is worth a specific caution here, because the intuitive story ("FP8 doubles your FLOPS, so it makes you more compute-bound") isn't quite right for decode. FP8 weights are stored in 1 byte instead of BF16's 2, so for the same batch size, decode's matmul arithmetic intensity roughly doubles too, since half as many bytes move for the same FLOPs. ## 3. Arithmetic Intensity and the Roofline Test
Section titled “3. Arithmetic Intensity and the Roofline Test” Arithmetic intensity is the amount of useful math you perform for each byte you move from the slower memory tier. In a roofline model, you compare arithmetic intensity against the hardware ratio of peak compute to peak memory bandwidth. If the workload’s arithmetic intensity is below that ratio, the workload is memory-bound. If it is above that ratio, the workload can become compute-bound, assuming kernels, scheduling, and software overhead are not the new limiting factor.
Use this simplified relationship as the starting point. Arithmetic intensity equals useful FLOPs divided by bytes transferred from slow memory. A decode step for a dense model does roughly two floating-point operations per parameter per active sequence, while the weights occupy `parameters x bytes_per_parameter`. If batch size is one and the weights are FP16 or BF16, the simplified decode intensity is roughly one FLOP per byte before considering KV traffic. That is far below the roofline threshold of modern tensor-core GPUs.

Why GPUs work so well

Deep learning inference is overwhelmingly matrix multiplication. A transformer layer is basically a few big matmuls plus attention, and matmuls are perfectly regular: same operation repeated over a grid, no branching, no unpredictable memory access. That's the easiest possible thing to parallelize, so you can throw thousands of simple arithmetic units at it. Modern NVIDIA GPUs have dedicated matrix hardware called tensor cores that do small tile multiply-accumulates in low precision, FP8 and NVFP4 rather than full 32-bit floats, which roughly doubles or quadruples useful throughput per watt for a modest accuracy cost.

But the deeper reason is memory bandwidth, and this is the part people get wrong. Inference has two phases with completely different characters. Prefill, where your whole prompt gets processed at once, has lots of math per byte of data, so it's compute-bound and cares about teraflops. Decode, generating tokens one at a time, is brutal: every single output token requires reading essentially the entire model's weights again. A 70-billion-parameter model at two bytes per parameter is 140 gigabytes of weights to stream per token, and an H100 moves about 3.35 terabytes per second, so that's roughly 42 milliseconds per token as a hard floor before any software overhead. The ratio of math to data movement in decode is around one flop per byte for a single sequence, while an H100's own compute-to-bandwidth ratio is near 300 flops per byte. That gap is why a decode step uses a tiny fraction of a GPU's advertised peak compute, and why the roofline model matters more than the spec sheet: you're stuck on the memory side of the line no matter which GPU you buy.

So GPUs win because they pair massive parallel matmul throughput with high-bandwidth HBM memory, plus software that keeps all those units fed: fused kernels, paged attention, quantization, speculative decoding, continuous batching. And crucially, one chip serves everything. The same card does training, fine-tuning, prefill, decode, vision encoders, recommendation models, and whatever architecture ships next year.

A GPU is a general-purpose parallel processor.
