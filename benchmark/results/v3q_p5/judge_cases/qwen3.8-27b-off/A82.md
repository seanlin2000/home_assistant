Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

**The three concepts**

An **API** is just a contract: a defined way for one program to ask another to do something or hand over data. A REST endpoint, a database query interface, a system call — all of them are APIs in some form. An API says "here's what you can ask me, and here's the shape of my answer." It doesn't care who's asking or how many times.

A **software tool** is a concrete program that does one job well — a calculator, a text scraper, a file converter. Tools are usually self-contained: they take input, produce output, and don't assume anything about their caller. A tool can be used through an API, but the word "tool" emphasizes the thing itself rather than the interface it exposes.

An **MCP server** is a specific kind of program that speaks the Model Context Protocol — Anthropic's open standard for connecting LLMs to external capabilities. It wraps tools, data sources, and prompt templates behind a standardized JSON-RPC interface (over stdio for local processes or Streamable HTTP for remote ones). The key difference from a plain API is *who it's designed for*: MCP servers advertise their capabilities dynamically so an LLM host can discover them at runtime, decide which one to call, and feed results back into the conversation. A regular API is static — you have to hard-code what it does somewhere in your prompt or code. An MCP server announces itself.

**Architecting web search + retrieval + summarization for a local LLM**

Here's how I'd structure it:

1. **MCP host (your application layer).** This is the program that owns the conversation loop. It maintains the chat history, calls your local LLM, intercepts tool-call requests, routes them to the right MCP server, and feeds results back. You can use an existing host like Ollama's Open WebUI, LM Studio, or build a thin Python/TypeScript wrapper around your model of choice (Llama, Mistral, etc.).

2. **One MCP server for search.** Expose a single tool, say `web_search(query)`, that calls a search API — Brave Search, Serper, DuckDuckGo's free endpoint, or SearXNG if you want it fully local. The server handles the HTTP call, parses results, and returns structured JSON with titles, URLs, and snippets.

3. **One MCP server for page retrieval.** A `fetch_page(url)` tool that grabs a URL, strips HTML to clean text (using something like `trafilatura` or `readability`), truncates to a sensible token budget, and returns the body. Keeping this separate from search lets you tune each independently — search might have rate limits, retrieval might need timeout and retry logic.
