Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Happy to. These three concepts sit at different layers, so thinking of them in terms of "what is the contract, what is the package, and what is the thing that gets called" keeps them straight.

An API is the most general idea. It is a contract for how one piece of software talks to another: which endpoints or functions exist, what you send, what comes back. A web service like a search engine's query API, or even a library's function signatures in code, are all APIs. An API says nothing about who is on the other end or why they are asking.

A software tool is one discrete capability a program can invoke to get a job done: fetch this URL, run this calculation, look up this record. A tool is usually a function with a name, an input description, and an output. Tools are what an API is often made of, but the word "tool" carries the implication that an agent — a human or a program making decisions — is choosing when to use it.

An MCP server sits on top of those ideas. Model Context Protocol is an open standard, announced by Anthropic in late 2024, that standardizes how AI models connect to external systems. Instead of every app inventing its own way of wiring up tools, MCP says: you run a small server that advertises a menu of tools, each with a name, a description, and a typed input schema. A client — the app hosting the model — discovers that menu and lets the model pick which tool to call and with what arguments. The big architectural point is that the LLM does not execute anything itself. It emits a structured request naming a tool and its arguments, the MCP client passes it to the server, the server does the actual work — hitting the network, reading a file — and returns a result the client feeds back to the model as context.

Now for your local web-search LLM. Here is how I would lay it out, roughly in the order a request would flow through it.

At the bottom you have the actual workhorses. A search tool that calls a real search engine's API — either a hosted one like Brave or SerpAPI, or a self-hosted stack like SearXNG if you want it local and private. That returns a handful of result titles and URLs, not full pages. A fetch tool that takes one or more URLs, downloads the page, strips the HTML down to text, and hands back the readable content — truncated to a budget so a giant page cannot blow up your context window.

You wrap those two functions in a tiny MCP server. The server exposes exactly those two tools with clear descriptions — "search the web and return titles and URLs," "fetch and extract text from a URL" — because the quality of those descriptions is what determines whether your model calls the right tool at the right time. That is the whole server. No intelligence in it, just plumbing.

The client side is a small local harness — an LLM server like Ollama, or a framework like llama.cpp, with a tool-calling loop around it. The loop is the heart of the system: it sends the user's question plus the tool menu to the model; when the model responds with a tool call instead of an answer, the harness executes it, appends the result as a new message, and sends everything back to the model; it repeats until the model produces a final text answer. That loop is the only "orchestration" you need, and it is deliberately dumb — all the judgment lives in the model.

One design choice worth calling out: I would not give the model a separate "summarize" tool. Summarization is a language task, not a retrieval task, so the LLM should do it itself in the final step. What you do want is to manage the raw material: the fetch tool should return only the top portion of each page — enough to summarize from — because most local models have a limited context window. If you expected the model to handle whole long documents, then yes, you would add chunking on the server side, but for page summarization, truncation plus a good final pass is simpler and usually works well.

Two practical tips. First, the tool descriptions are where a lot of the tuning happens — if your model fetches pages it should not, or searches when it should answer from what it already has, rewrite the descriptions to be more prescriptive. Second, keep results short on the way back in: five search hits and a few hundred words per page is plenty, and it keeps the context window clean for the model to actually reason about the content.

If your local model's context window is large enough — a modern local model in the 128k-token range, for instance — you can be generous with how much of each page you return and let the model do heavier synthesis. But with smaller models, be strict about truncation, or the whole thing quietly degrades.

In one sentence: the API is how the search engine talks to the world, the tools are your two named capabilities, and the MCP server is the standardized wrapper that makes those tools discoverable and usable by the model without custom glue code per app.
