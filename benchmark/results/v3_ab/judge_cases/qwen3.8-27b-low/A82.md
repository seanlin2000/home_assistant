An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

## Frequently Asked Questions
### What is the difference between MCP and function calling?
Function calling is the LLM emitting structured JSON that names a tool and its arguments — it is a model capability. MCP is the protocol that lets tool servers and clients describe, discover, invoke, and return those tools across processes — it is an interop layer. They cooperate: the client converts MCP tool definitions into the model's function-calling format, the model emits a function call, the client maps the call back to an MCP server, and the server runs it. Without MCP you can still do function calling; you reimplement filesystem/database/browser handlers per project. With MCP, the same servers work under any client.
### Can I use Claude Desktop with Ollama models?
Not as a direct setup. Claude Desktop talks to Anthropic's cloud models, so it does not run an Ollama model. What carries over from Claude Desktop is the MCP server ecosystem: the same servers work with an MCP client that does support Ollama, such as Goose, Cline, Continue.dev or LM Studio. ASSISTANT: Good question, and the three terms overlap more than they should. Let me untangle them.

An API is a generic contract — a defined way for one program to ask another for something and get something back. It's the shape of the request and response, usually over HTTP or JSON-RPC. Your web browser uses APIs, your phone's weather app uses APIs, Ollama itself exposes an API on localhost port 11434. An API is a protocol-agnostic idea; it doesn't say anything about who's calling it or what they're doing with the result.

A software tool, in the LLM world, is a specific capability a model can invoke — a named function with a description and typed parameters. When a model decides it needs to look something up, it emits a structured JSON call that names the tool and fills in its arguments. The tool itself is usually just a function in your own codebase, or a wrapper around some API. Tools are model-specific: the schema has to match whatever function-calling format the model expects.

An MCP server is a standardized package of tools that speaks the Model Context Protocol. It's a small program — often a Python or Node script — that describes its tools in a canonical format, communicates over stdio or HTTP using JSON-RPC, and handles the tool calls. The key difference from a raw tool is portability: the same MCP server works under Claude Desktop, LM Studio, Continue, Cline, Goose, or a custom client you write yourself. Function calling is the model's ability to emit a tool call; MCP is the plumbing that lets any client discover, invoke, and get results from tool servers without writing custom adapters for each one.

Now, your architecture for a local LLM that searches the web, fetches pages, and summarizes them. As of right now, Ollama itself doesn't natively speak MCP — that feature request is still open. So you need a bridge layer. Here's what I'd actually build.

At the bottom, a local model with reliable tool calling. As of this year, Qwen 3.5 in the 9B range or Gemma 4 are the strongest starting points for function calling among local models. Run them under Ollama or LM Studio, both of which expose an OpenAI-compatible API on localhost.

On top of that, an MCP client that acts as the bridge. This is the piece most people miss. Your options are a desktop app like LM Studio, which has had built-in MCP client support since early 2026, or a framework like Continue.dev, Cline, or Goose, or you write a thin Python client using the MCP SDK that talks to Ollama's chat API and shuttles tool calls between the model and the MCP server. That client converts MCP tool schemas into the model's function-calling format, lets the model emit a call, routes it to the right server, and feeds the result back.

Then the MCP server itself, which in your case is a web tool server. It exposes at least two tools: a search tool that takes a query and returns top results with titles, URLs, and snippets, and a fetch tool that takes a URL and returns the page's main text, cleaned of navigation and boilerplate. The search backend can be anything — Brave Search API, Tavily, Serper, or a local search index if you want zero cloud dependency, though that's a much harder problem. The fetch side is just an HTTP client with a readability step, and you'll want to truncate aggressively because local models have limited context and you don't want a 50,000-token Wikipedia page blowing out the window.

Summarization happens in the model itself, not in the MCP server. After the model fetches a page, the client feeds the page text back into the conversation as the tool result, and the model summarizes it in its next turn. You can structure this as a multi-step agent loop: model calls search, client returns results, model picks a URL and calls fetch, client returns the page, model summarizes. Some clients handle this loop automatically; if you're writing your own, it's a while loop that keeps calling the model until it stops emitting tool calls.

One practical warning: local models are noticeably less reliable at multi-step tool calling than frontier models. If your model keeps hallucinating tool names or malformed JSON, that's the first thing to check before blaming the plumbing. The 9B and 12B class models handle two or three sequential tool calls well; beyond that you start seeing errors. If you need robustness, bump the model size or consider running the whole loop in a framework like Cline or Goose that has built-in retry and recovery logic.
