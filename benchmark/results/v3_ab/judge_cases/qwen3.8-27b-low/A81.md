Reference sketch (what a correct answer must contain):
The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. Websites the assistant then fetches see the IP address and the requests. What stays local: the audio and transcription if speech is processed locally, the full conversation and history, the model's reasoning and answers, and anything never put into a query. Minimizing exposure: keep personal details out of queries (write queries from the question, not the whole conversation), search only when needed, cache results, use a privacy-focused provider or a self-hosted metasearch proxy such as SearXNG, route through a VPN for IP privacy, and check the provider's data-retention terms.

# Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: Good question, and it's one where the mental model is actually pretty clean once you separate the two systems.

The key insight is that the search provider only ever sees what your code explicitly sends it. Your local model, the conversation history, your files, your reasoning, your other prompts, all of that stays on your machine. The only thing that crosses the wire is the HTTP request your agent code makes to the search API.

So what does that request actually contain? At minimum: the search query string, which is the most sensitive part; an API key, which identifies your account; and your IP address, which every server you connect to can see automatically. Depending on the API and your client library, there may also be a user-agent string that reveals your operating system and library versions, request headers, and if you use optional parameters, things like the number of results you want, a time filter, or a location hint.

What the search provider does not see: your conversation with the model, the model's chain of thought, any files on your disk, your system prompt, the parts of your question that the model decided not to put in the search query, and the model's final answer unless you separately transmit it somewhere.

Now, for minimizing exposure, the most important lever is the query itself. If your agent code naively passes the user's full question to the search API, you're sending potentially sensitive context to a third party. The better pattern is to have the model produce a minimal, sanitized query — just the keywords it actually needs. You can enforce this in your agent prompt, or even in code by stripping things that look like personal data before the request goes out.

A few other practical steps. Use a dedicated API key for the search service so a leak there doesn't compromise anything else. Pick a provider with a privacy policy you're comfortable with; Brave's search API, for example, states it doesn't log query content, while others may retain it. Run a local logging layer that records exactly what's being sent so you can audit it. And if you're really security-conscious, you can put a small local proxy in front of the search API that sanitizes or caches queries before forwarding them, which also gives you a place to enforce policies.

One thing people sometimes overlook: even if the search provider's policy says they delete queries after X days, your IP address and the timing of your requests are still correlated with your account in their logs. So "anonymity" from the provider is really about minimizing how much content you send, not about hiding that you made a request at all.
