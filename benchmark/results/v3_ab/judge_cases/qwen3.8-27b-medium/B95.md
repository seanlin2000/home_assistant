The core constraint that shapes everything: natural conversation through a *local* model means your hardware budget mostly has to buy LLM inference speed. With a thousand dollars you can't get GPT-grade responses, but you can get something that feels like a real assistant with a few smart choices.

The architecture I'd propose is a classic cascade rather than one giant end-to-end model, because each piece is cheaper and more swappable:

A wake-word and voice-activity detector, like OpenWakeWord or Picovoice, plus Silero's VAD. This is the part that listens constantly and cheaply so the rest of the system sleeps. Speech-to-text with faster-whisper, running a small model like tiny or base. The brain is a quantized open-weight LLM, in the eight-to-fourteen-billion-parameter range, running under llama.cpp or Ollama, with a system prompt and a function-calling layer for tools. Text-to-speech with Piper, which is fast and runs comfortably on modest hardware. Tools are then three things: a web-search function (a local scraper of DuckDuckGo's HTML, or a keyed API like Tavily), Home Assistant for smart-home control through its REST API or WebSocket, and a SQLite database for conversation memory.

For hardware, two viable shapes fit the budget. My top pick: a Mac mini with an M4-class chip and sixteen gigabytes of unified memory — that lands somewhere around nine hundred to a thousand dollars new. Unified memory is what makes it work, because a quantized eight-billion model fits in about six gigabytes and you still have headroom, and Apple Silicon gets you roughly ten to twenty tokens per second on those models, which is the threshold where spoken answers feel tolerable. The alternative is a used or mini-ITX PC with about twelve to sixteen gigabytes of VRAM in the GPU, which also fits budget and is easy to upgrade later. I'd skip a Raspberry Pi as the brain — it's fine as a satellite for the mic array, wake word, and TTS, but it will choke on the LLM and your conversation will take a minute per answer. A Pi running wake-word, VAD, and TTS next to a Mac mini or GPU box running whisper and the LLM is a nice layout, but it's an optimization, not a starting point.

Now the honest limitations, in order of how much they'll hurt:

Latency is the big one. Even on good hardware, end-to-end you're looking at several seconds from you finishing speaking to the first word coming back — wake word, transcription, model warmup, generation, synthesis. It won't feel like a two-way conversation with interruptions; it will feel like a very good push-to-talk system unless you engineer streaming generation into Piper and trim every stage. That's the single most important expectation to set.

Tool calling is the second limitation. Open-weight models of this size are noticeably worse at reliable function calling than frontier models. You can get it working — Home Assistant on/off calls, search lookups — but expect occasional malformed calls and you'll want retries and strict schemas. Keep the tool set small, under five functions, or the model starts flailing.

Web search quality is third. A locally-scraped search returns worse results than what a commercial assistant gets, and you should plan for the search results to be summarized by your model, not quoted verbatim. This is the one capability where a hosted API behind a local proxy will make the biggest quality difference if you ever decide to relax the "fully local" rule — it's the easiest seam to open later.

And memory is quiet but real: keeping conversation history in context burns tokens and slows things, so you'll want rolling summaries rather than raw history.

On build order, I'd do it in three phases. First: the push-to-talk loop — one mic, one speaker, whisper, the LLM, Piper, keyboard-free from day one. Get one question asked and answered in voice end-to-end before touching anything else, because that loop decides which model size actually feels acceptable on your machine, and that decision drives everything downstream. Second: wire up Home Assistant with three or four simple tools, since smart-home control is where a local assistant beats a phone app — no cloud, instant, works offline — and it validates your function-calling layer on forgiving, low-stakes commands. Third: add the always-on wake word, barge-in handling, rolling memory, and web search. Search last on purpose, because it's the least reliable piece and the least unique to a local build.

If I had to compress it: buy the inference box first, build the push-to-talk loop second, and treat everything else as bolt-ons to that spine.
