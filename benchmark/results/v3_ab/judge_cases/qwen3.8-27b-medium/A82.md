Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Great question. Let me work through the three terms first, then the architecture.

An API is just a contract between two pieces of software. One program says "here's how you can talk to me," and the other one speaks it. A weather service, a payment gateway, a database query interface — all APIs. They're the lowest-level building block, and they're what everything else in your stack will be built on.

A software tool is a general term for a program that does a specific job. A text editor, a file converter, a scraper — any of those. A tool can be a command line app with no network at all, or it can wrap an API. "Tool" describes the purpose; "API" describes the interface. The two words overlap but aren't the same axis.

An MCP server — Model Context Protocol — sits one level up. It's a standardized way of exposing capabilities, like web search or file access, to AI models. Instead of each LLM integration hand-rolling its own glue code to call a tool, the tool's author writes an MCP server that advertises its functions in a standard format — names, descriptions, parameters — and any MCP-aware model or client can discover and call them. So an MCP server is really a tool plus a standard wrapper that makes it discoverable by an LLM. The API might sit underneath, the MCP server sits on top, and the LLM talks to the MCP server without knowing the details.

Now, for your local LLM that searches, retrieves, and summarizes. I'd split it into four layers.

First, the tooling layer. Two concrete tools: a search tool that wraps a search API — for local use I'd suggest something like Serper, Tavily, or a self-hosted SearXNG if you want to keep queries off third parties — and a retrieval tool that fetches a URL and extracts clean text, handling things like stripping navigation, and ideally falling back to a reader service if the raw HTML is messy. These two can be written as a single MCP server with two exposed functions, search and fetch. One server is simpler than two here since the functions are closely related.

Second, the local model layer. A model strong enough to both use tools and produce a decent summary. For something running locally as of now, I'd look at the mid-size quantized models — an 8 to 14B parameter model with good function-calling support, or a larger MoE model if you have the hardware, since MoE models give you good quality at moderate inference cost. The model needs reliable structured output, because it has to emit tool calls in the right format, not just prose.

Third, the orchestration loop. This is the actual agent logic: the model sees the user's question, decides it needs a search, emits a search call, gets back the top results, picks the most relevant ones, calls fetch on those, and then reads the retrieved text and writes the summary. Your orchestration code just loops — run the model, if it emitted a tool call run the tool and feed the result back, repeat until the model produces a final answer. I'd set a cap on iterations, maybe five or six, and a cap on how many URLs get fetched per query, so you don't end up pulling ten pages for a simple question.

Fourth, a few practical choices worth calling out. Keep summaries per-page first, then have a final model pass condense the individual summaries into one answer, rather than stuffing full page text into context — full pages will blow your context window and dilute attention. Cache retrieved pages by URL with a short TTL so repeated runs are fast. And because your model is local and your search is possibly self-hosted, this whole pipeline stays private, which is probably part of why you're doing it locally.

The one question I'd ask before you commit hardware: how much RAM and what GPU do you have? That decides whether you're running a small fast model or a larger one, and it's the single biggest constraint in this architecture.
