Reference sketch (what a correct answer must contain):
The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. Websites the assistant then fetches see the IP address and the requests. What stays local: the audio and transcription if speech is processed locally, the full conversation and history, the model's reasoning and answers, and anything never put into a query. Minimizing exposure: keep personal details out of queries (write queries from the question, not the whole conversation), search only when needed, cache results, use a privacy-focused provider or a self-hosted metasearch proxy such as SearXNG, route through a VPN for IP privacy, and check the provider's data-retention terms.

# Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: Here's the core thing to understand: the search provider sees exactly what your code puts into the HTTP request, and nothing else you haven't chosen to send. So the interesting question isn't really what gets leaked, it's what your code sends, because a lot of people are surprised.

What goes out over the wire. At minimum, the provider receives the search query itself, your IP address, which gives you approximate location and your internet service provider, the timing of the request, and whatever headers your code adds. That includes your API key, which identifies you as a specific customer, and a User-Agent string that can reveal your operating system and software. Some libraries and SDKs add more, like device identifiers, telemetry fields, or your geographic coordinates if you've enabled location. And here's the subtlety: the query is usually composed by the local model from the conversation. So if you asked your assistant to "draft an email to my landlord about the leak," the model may send a query containing your topic, your situation, names, or addresses. The provider never sees your conversation, but it sees a query distilled from it, and that query is often more sensitive than you realize.

What stays local. The full conversation history, the prompt you gave the model, the model weights, the model's reasoning and output, and anything on your disk. The search results come back to you, and you can do whatever you want with them. The provider knows it answered a query, not what you did with the answer.

How to minimize exposure. First, audit what actually leaves: log the outgoing request, or put a proxy in front, and you'll see the real payload instead of assuming. Second, constrain the query. Tell the model to produce only short, minimal keyword queries, and if you handle sensitive topics, add a sanitization step where the model rewrites the query with names, addresses, and other personal details stripped out before it's sent. Third, clean up your headers. Don't send conversation context, don't include location unless necessary, and use a neutral User-Agent. Fourth, if you care about IP exposure, route requests through a VPN or a proxy you control. Fifth, pick the provider deliberately: read their data-retention and logging policy, and prefer ones with a short retention period and a real privacy commitment. Or, if you want to eliminate the third party entirely, run your own SearXNG instance, which gives you the same web results through infrastructure you own. And finally, treat TLS as table stakes: it stops your network from eavesdropping, but it does nothing about the provider itself.

One caveat: I'm speaking generally about how these APIs work. Logging and retention specifics vary a lot by provider, so check the policy of whichever service you actually use before you trust it.
