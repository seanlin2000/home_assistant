Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Great question. Let's break it down in layers, because these terms sit at different levels of abstraction.

A software tool is the broadest concept: any program that performs a task. A calculator, a web browser, or a script that scrapes a website are all tools. They exist independently of any AI.

An API — Application Programming Interface — is a specific way for one piece of software to talk to another. It's a contract: "if you send me this JSON with these parameters, I'll give you back this JSON." When you call a weather service by sending an HTTP request to its endpoint, you're using an API. APIs are how tools expose their functionality to other programs in a structured, predictable way.

An MCP server — Model Context Protocol server — is a newer standard that sits on top of APIs and makes them consumable by LLMs specifically. Think of it as an adapter layer. An MCP server wraps one or more underlying capabilities (which might be APIs, local file access, databases, whatever) and exposes them to any MCP-compatible AI client through a standardized protocol. The LLM doesn't need to know the specifics of how web search works; it just sees a list of available tools with descriptions, and can call them by name with arguments. MCP is essentially "USB-C for AI tool access" — one standard interface that lets you plug in any capability.

Now, for your architecture — giving a local LLM web search, page retrieval, and summarization:

I'd structure it in three layers.

At the bottom, you have your actual capabilities. A web search function that calls something like the Serper or Tavily API, or even just hits DuckDuckGo's HTML endpoint if you want to stay fully local with no keys. A page fetcher that takes a URL, pulls the HTML, and strips it down to clean text — something like Python's requests library combined with BeautifulSoup or a readability extractor. And a summarizer, which is really just your LLM itself prompted to condense text.

In the middle, you wrap those capabilities in an MCP server. You define three tools: "search_web" that takes a query and returns a list of results with titles, URLs, and snippets; "fetch_page" that takes a URL and returns the cleaned text content; and optionally "summarize" if you want it as an explicit step rather than letting the model do it inline. Each tool gets a clear name, a description the LLM can read, and a schema for its parameters. You run this MCP server locally, say over stdio or a local HTTP endpoint.

At the top, your local LLM client — whether that's Ollama, LM Studio, llama.cpp with an MCP-aware frontend, or a custom Python loop — connects to your MCP server. The user asks something like "What are the latest developments in solid-state batteries?" The LLM sees its available tools
