Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Good question. Let's take these one at a time.

A software tool is just any program that does a specific job. A calculator, a text editor, a weather app—those are all tools. It's the broadest term in your list, and it doesn't say anything about how you're supposed to use the thing.

An API is a way for one piece of software to talk to another. It's a set of rules that says, "here are the requests I'll accept, here's what I'll send back." You can call an API over HTTP, through a library, or in a bunch of other ways. The key idea is that it's a contract between two systems, and it lets you use the functionality of one program from inside another without having to rewrite the code yourself.

An MCP server is a specific kind of tool wrapper built around the Model Context Protocol. It takes capabilities—like web search or file access—and packages them in a standardized way that any MCP-compatible AI client can discover and call. So it's really an API with a particular structure designed for LLMs, where the model itself decides when and how to use each capability based on what you ask it.

Now, for your architecture question. If I wanted to give a local LLM web search, page retrieval, and summarization, I'd build it in layers.

First, the LLM itself, running locally. This is the brain that understands your request and decides what to do next. It doesn't have direct internet access on its own, so it needs tools.

Second, an MCP server, or a set of them, that exposes three clear capabilities. One for searching the web, which would call out to a search API like SerpAPI or DuckDuckGo's endpoint and return structured results. One for fetching a webpage, which takes a URL, pulls the HTML, strips it down to clean text, and hands that back. And one for summarization, which either uses the LLM itself in a second pass with a focused prompt, or calls out to a summarization model if you want something lighter.

Third, an MCP client layer sitting between the LLM and those servers. This is what actually translates the model's tool calls into real requests to your MCP servers and feeds the results back. There are open-source clients you can run locally that handle this plumbing for you.

The flow would look like this: you ask the local LLM a question. It reasons about what it needs, sends a tool call to the search capability through the MCP client, gets back a list of URLs and snippets. It picks the most relevant ones, calls the fetch capability on each, gets clean text back. Then it either summarizes directly in its own response, or calls the summarization tool if you want a tighter output. The whole loop is driven by the model's own judgment about what to do next.
