USER: Imagine I want to build a private, locally hosted voice assistant that can answer general questions, search the web, control smart-home devices, and have natural conversations. I have a $1,000 hardware budget. Propose an architecture, explain the components, identify the biggest limitations, and prioritize what I should build first.

ASSISTANT: Here's how I'd think about this build.

The architecture is a pipeline: wake word detection, speech-to-text, a language model that reasons and decides what to do, a tool-calling layer that actually acts on the world, and text-to-speech to speak the result back. Each stage has a well-matched open-source option that runs locally, and the whole thing is held together by a small Python or Node.js orchestrator.

**Wake word.** Something like openWakeWord or Picovoice Porcupine. These are tiny neural networks that listen for a phrase and fire an event. They run on a CPU with almost no overhead, so they don't compete with the GPU for resources.

**Speech to text.** Whisper, specifically the faster-whisper or whisper.cpp implementation. The "small" or "base" model gives you a good speed-to-accuracy tradeoff for a voice assistant. You don't need the large model; you want sub-second latency, and the smaller models deliver that on a mid-range GPU. If you want even lower latency, there are streaming variants that process audio in chunks as it arrives rather than waiting for the full utterance.

**The language model.** This is where most of your budget goes, and it's also where the biggest tradeoff lives. I'd recommend running a 7B to 13B parameter model through Ollama or llama.cpp. By late 2026, models in that range—think Llama 3.1 8B, Qwen 2.5, or Mistral-class models—are genuinely good at following instructions, maintaining a conversation, and making structured tool calls. You do not need a 70B model for a voice assistant. What you need is a model that's fast, well-instructed, and reliable at outputting the right function call at the right time. A 13B model at Q4 quantization fits comfortably in 12 to 16 gigabytes of VRAM.

**Text to speech.** Piper is my first pick. It runs on CPU, produces natural-sounding speech, and has a huge library of voices. It's fast enough that you barely notice the gap between the LLM finishing and you hearing the reply. If you want something a touch more expressive, Kokoro TTS is a strong second option that's also very efficient.

**Smart home.** Home Assistant is the obvious backend. It has a REST API and a WebSocket API, and it speaks to nearly every smart-home protocol—Zigbee, Z-Wave, MQTT, cloud-based devices. Your orchestrator passes the LLM's tool call to a thin wrapper that translates it into a Home Assistant API request. The LLM never touches the network directly for home control; it just says "turn on the kitchen light" and your code does the rest.

**Web search.** This is where I have to be honest with you: "private" and "web search" are in direct tension. The open web is not something you can replicate locally. Your options, in order of privacy, are: first, a local RAG index over documents you've chosen to put in scope, which covers a lot of "general questions" without any network call. Second, calling a privacy-oriented search API like DuckDuckGo's, which does go out to the network but doesn't build a profile. Third, a full search engine API, which is least private but most capable. I'd build the RAG layer first and treat web search as an optional, explicitly user-triggered tool so you always know when the assistant is reaching out to the internet.
