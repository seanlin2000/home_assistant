Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: These three terms overlap a lot in casual conversation, but they sit at different layers. Think of it like a stack.

An API is the bottom layer and the most general. It is just a defined way for one piece of software to ask another for something and get an answer back, usually over HTTP. You send a request, you get a response. A search engine, a weather service, a database, all of those expose APIs. An API says nothing about who is using it or what they want to do with the result.

A software tool is a bit more specific. It is a function or a small program that does one concrete job. It might be pure local code, like "read a file" or "run this calculation," or it might be a wrapper around an API, like "call the search engine and hand me back the results." A tool is the unit of work. The word comes from the LLM world, where a model is told "here are these functions you can call," and picks one when it needs to.

An MCP server, short for Model Context Protocol, is the layer on top. It is an open standard, originally from Anthropic, that gives a uniform way to describe, discover, and invoke tools for AI systems. Instead of every AI app hand-rolling how it talks to a particular tool, an MCP server publishes its capabilities using a shared format, and any MCP client can pick them up. So MCP is less a new kind of thing and more a universal adapter: it standardizes the handshake between a model and its tools. You could run the same search tool either as a plain function or exposed through an MCP server; the second option just makes it plug into any compatible AI app.

Now the architecture for your goal. You want a local model that can search the web, pull pages, and summarize them. I would build it as a loop, not a single call.

Start with the local model doing the orchestration, running through something like Ollama or llama.cpp. You give it a small set of tools it can call. The first tool, search, wraps a real search API. For this I would use a dedicated search API like Brave, Tavily, or SerpAPI, because a plain scraper of DuckDuckGo is fragile and you want clean, ranked results with URLs. That is your API, wrapped into a tool.

The second tool is retrieve, which takes a URL and fetches the page. Here the important trick is cleaning: raw HTML is noisy and blows through your context window, so you strip it to readable text with something like a readability library or trafilatura before the model ever sees it. If the page is long, you chunk it or truncate to what fits.

The third step, summarization, is not really a separate tool at all. It is just the model being called again, this time with the retrieved text in its prompt and an instruction to summarize. So your pipeline is: the model decides what to search, calls the search tool, reads the results, calls retrieve on the best one or two URLs, and then it does the summarizing on its own because it is already the summarizer.

The loop is the key idea. The model sees the search results, may decide they are not good enough, and searches again with different terms; it may grab a page, find it unhelpful, and move on. That is why you expose tools to it rather than hard-coding a one-shot sequence.

A few practical notes for a local model specifically. Local models are weaker at tool-calling discipline than big cloud models, so keep the tool set tiny and the descriptions very clear, and give the model a few worked examples. Also, local context windows are often smaller, so be aggressive about trimming retrieved text. If you find the local model is not orchestrating well, a common pattern is to use a strong frontier model just to plan and decide what to search, and keep the local model for the cheaper summarization of results. And if you want portability so any app can use these tools, package search and retrieve as an MCP server rather than raw functions.

So in one breath: an API is a doorway to a service, a tool is a job your code does, and MCP is the standard way to hand those tools to an AI. And your system is a local model in a loop, calling a search tool and a fetch tool, then summarizing the results itself.
