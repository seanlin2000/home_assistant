The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. # Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: Great question, and one that a lot of people gloss over. The short answer is: the search provider sees far less than you might fear, but there's still a meaningful slice of your activity that leaves your machine.

Here's the breakdown.

**What stays local:**

The model weights, of course. But more importantly, your full conversation history, your system prompt, any files or documents you've loaded into context, and the model's own reasoning about how to interpret and synthesize the results. None of that crosses the wire. The LLM is generating tokens on your own hardware, and that process is invisible to anyone else.

**What gets transmitted to the search provider:**

The main thing is the search query itself. That's the payload you send in the API request. Beyond the query text, the provider also sees your IP address, a timestamp, and whatever identifying headers are attached, which typically includes an API key that ties the request to your account. Some providers, depending on their logging practices, will retain the query string, the number of results returned, and sometimes the full result set they served you.

Here's the subtle risk: if your local orchestration code is sloppy and it passes a chunk of your conversation context into the search query, that context now leaves your machine. So the query is the boundary, and the quality of your code determines how much you leak through it.

**How to minimize exposure:**

First, keep queries short and generic. If you're asking the model "look up the latest FDA guidance on this compound I'm researching for a client," don't send the client's name or your research notes in the query. Strip anything personal or identifying before the request goes out.

Second, check the provider's data retention policy. Some, like SerpAPI, store your query history in your dashboard. Others are more ephemeral. If retention matters to you, that's a real differentiator.

Third, consider whether you actually need a third-party API at all. You can run a local meta-search engine like SearXNG, which hits public search endpoints on your behalf. It's less polished, but the query never touches a company that logs it to an account.

Fourth, if you do use a commercial API, use a dedicated key that you can revoke, and check whether the provider offers a "no logging" or "zero retention" tier, which some now do for privacy-sensitive workloads.

Fifth, be aware that even the pattern of your queries, when, and how often, is metadata. If you're doing something sensitive, the fact that you searched for it at all is the exposure, not just the words.

So the architecture is actually reasonably clean by default. The real risk is in the glue code between your local model and the API, and in how much context you're willing to let leave the box.
