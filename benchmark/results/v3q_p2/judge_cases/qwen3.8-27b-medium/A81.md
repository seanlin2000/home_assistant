Reference sketch (what a correct answer must contain):
The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. Websites the assistant then fetches see the IP address and the requests. What stays local: the audio and transcription if speech is processed locally, the full conversation and history, the model's reasoning and answers, and anything never put into a query. Minimizing exposure: keep personal details out of queries (write queries from the question, not the whole conversation), search only when needed, cache results, use a privacy-focused provider or a self-hosted metasearch proxy such as SearXNG, route through a VPN for IP privacy, and check the provider's data-retention terms.

# Exchange 1

USER: If I run a language model locally on my computer but use an external web-search API, what information can the search provider see? Explain what stays local, what gets transmitted, and how I can minimize data exposure.

ASSISTANT: Good question, and the short answer is: far less than most people worry about, but a bit more than "just the search term" — it depends on how the software is wired.

What stays local. The model's weights, the full conversation history, everything the model generates, and any files you keep on disk never leave your machine. The search provider is not your model host. It's a plain API, the same kind you'd call from a web app. It has no visibility into your chat unless your program explicitly sends parts of it.

What gets transmitted. At minimum, every request carries the search query itself, along with standard network metadata: your IP address, a timestamp, and headers like your API key, which identifies your account. Some providers also log the user agent and referer. The response — search results, snippets, links — comes back to you locally and then gets fed into your model's context, but that part is one-way inbound. The real exposure comes from what your local program puts in the request. Well-behaved tools send only a compact query string the model composed. Poorly built ones send the entire system prompt or even the whole conversation for the model to "decide" what to search, and in that case everything in your chat is on its way to the provider.

So the practical minimization steps are. First, check your tool's documentation or config for what exactly it sends — some let you log outgoing requests, and reading one or two is the fastest way to know the truth about your setup. Second, make sure it sends a minimal query and nothing else; if it can't, an intermediate layer — a small script that takes the model's question, strips it down to keywords, and calls the API — gives you control. Third, never paste secrets, credentials, or personal data into the chat expecting it to stay local if search is enabled, because a single careless query can quote it back. Fourth, the IP address is the one thing you can't control without a proxy, so if that matters, route the API calls through a VPN or proxy you trust. And fifth, read the provider's data retention policy — some log queries and snippets for a period, some claim not to — and use a dedicated API account so those logs, whatever they contain, are separable from your main life.
