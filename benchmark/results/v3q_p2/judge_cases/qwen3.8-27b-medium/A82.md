Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

# Exchange 1

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: Let's take these three apart, because they're often conflated, and they actually live at different layers of the stack.

A software tool is the broadest term. It's any program that does a job: a calculator, an image editor, a script that scrapes a website, a database. It has no particular contract about how other programs talk to it. You could use it from a command line, from a GUI, or from inside another program, and none of that is standardized.

An API is a specific contract for how one program talks to another. "Application Programming Interface" sounds abstract, but it just means an agreed-upon way to ask a program for something and get something back: here's the endpoint, here's the format of the request, here's the format of the response. The weather service I might call to answer a forecast question is an API. A REST API, a database query interface, even a command line can function as one if the inputs and outputs are well defined. The key idea is that the API describes the interface, not the implementation. You can swap the backend and anything calling the API keeps working.

An MCP server, Model Context Protocol server, is a newer, more specific thing, and it's worth understanding it as a tool plus an API plus some conventions, packaged for AI models. MCP is an open protocol, originally introduced by Anthropic, that standardizes how a language model can discover and call external capabilities. The protocol defines a client-server setup over a simple message format, and it has a few standardized request types: the client can ask the server to list its tools, ask for a tool's input schema, and then invoke a tool by name with arguments. So an MCP server is a small program that exposes tools to a model, and it does so through a standardized interface that any MCP-compatible model client can consume without custom integration work. That's the whole point: instead of every model client hand-coding how to talk to every tool, you get one protocol, and a growing ecosystem of compatible servers.

One nuance: an MCP server isn't fundamentally a different kind of program from a tool. It wraps a tool, or a collection of tools, and gives them an MCP-standardized front door. The same underlying web-search function might be callable from a command line, from a REST API, or from an MCP server. What changes is how the model discovers it, how it knows what arguments to pass, and how the result comes back.

Now for the architecture question. I want to give a local large language model the ability to search the web, fetch pages, and summarize them. I'd think about this in four layers.

First, the tool layer. These are the actual capabilities. A web search function that takes a query and returns a ranked list of results with titles, URLs, and snippets. A fetch function that takes a URL and returns the page as text. And a summarize step, which I'd actually want the model itself to do rather than a separate program, because summarization is exactly what a language model is good at, and I want it to summarize in the style the user asked for.

Second, the interface layer. This is where I'd use MCP. I'd write a small server, in Python or TypeScript, that exposes two tools: web_search and fetch_page. Each tool would have a name, a short description the model can read, and a JSON schema for its inputs. That schema matters a lot, because it tells the model exactly what shape of arguments to send. The fetch tool is where I'd do some real engineering: strip scripts and styles, convert HTML to readable text or markdown, cap the length so I don't blow up the context window, and handle timeouts, redirects, and 404s gracefully with a useful error message the model can react to.

Third, the client layer. This is the model's side of the MCP connection. Because you're running a local model, you'd want an MCP client that works with local inference, either something like an MCP client library you embed in a small app, or a harness that can run your local model, talk to the MCP server over a local connection like standard input-output or a loopback socket, and shuttle tool calls back and forth. The loop would look like this: the user asks a question, the model decides it needs to search, it emits a tool call for web_search with a query, the client sends that to the MCP server, the server runs the search and returns results, the client hands them back to the model, the model picks the most promising URLs and calls fetch_page, then once it has enough content, it stops calling tools and produces the summary in natural language. That last step is the important behavior to design for: you want the model to know when to stop fetching and just answer.

Fourth, the guardrails and glue. Because this is a local model, I'd want to be deliberate about a few things. Context management, so a long fetched page doesn't evict the conversation. Rate limiting and timeouts on the fetcher, because a model can occasionally get into a loop of fetching pages. A simple allowlist or blocklist for domains if you want to keep it well behaved. And logging of every tool call so you can see exactly what the model did, which matters a lot for debugging and for trust, especially when a model is autonomously deciding which URLs to fetch.

If I were going to keep it simple, I'd also mention a cheaper alternative to full MCP for a local setup: skip the protocol and just give the model a structured prompt that lists the available tools and their argument formats, and have your harness parse the model's responses for tool-call blocks and execute them in-process. That's fewer moving parts and works fine for a single local model. You pay for it when you start wanting that same model to talk to other tools, or to other people's tools, and that's the moment MCP starts to earn its keep.

One honest caveat, though: for a local model to be reliable at this, you want something with strong tool-calling ability and a decent context window. Smaller local models can be flaky about the exact JSON shape of tool arguments, and that flakiness is the number one source of friction in these architectures, more so than the network code. If your local model struggles, the fix is almost always in the prompt and the argument schemas, making them simpler and giving the model a couple of worked examples, rather than in the plumbing.
