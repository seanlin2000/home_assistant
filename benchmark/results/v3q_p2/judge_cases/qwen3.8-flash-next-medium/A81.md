Expected reply: an ordinary answer

Gates especially relevant here: none beyond the general rules

Reference sketch (what a correct answer must contain):
The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. Websites the assistant then fetches see the IP address and the requests. What stays local: the audio and transcription if speech is processed locally, the full conversation and history, the model's reasoning and answers, and anything never put into a query. Minimizing exposure: keep personal details out of queries (write queries from the question, not the whole conversation), search only when needed, cache results, use a privacy-focused provider or a self-hosted metasearch proxy such as SearXNG, route through a VPN for IP privacy, and check the provider's data-retention terms.

## Key Insights
- Real-time tracking : The 1-second window slides continuously, so your request count is always calculated for the most recent second.
- Counted on arrival : The request count is increased when request is received. The processing time does not affect the rate-limit.
- Multiple limits : Most plans have both burst limits (per-second) and quota limits (per-month) that must be respected simultaneously
- Successful requests only : Failed requests don’t count against your quota, so you’re only charged for successful API calls

ASSISTANT: Here's the picture, with the important caveat that the search API is the one place your "private" setup stops being private.

What stays local. The model weights, all the inference, your full conversation, your files and documents, and anything the model reasons about internally never leave your machine. Nothing about the conversation is sent to the search provider unless your software deliberately puts it into an API call.

What does get transmitted. Every API call carries a small bundle: the query string itself, your API key, your IP address, a timestamp, and usually a user-agent or client library string. The provider also sees how many requests you make and when, since rate limits are counted per key — Brave's API even returns headers showing your remaining quota, which means your usage pattern is tied to your account. Two subtleties worth understanding. First, the query is generated by the model, not by you, and models happily copy specifics out of your context into it. Ask your assistant a question about your apartment lease and the outgoing query may contain your street address, your landlord's name, and a clause from the document. Second, if your setup includes a fetch, crawl or extract tool, those calls reveal which pages you actually read, and the target websites themselves see your IP as well. Some providers also have "answers" or grounding endpoints that take your whole question rather than a short query, which sends more of your wording than you intended.

What providers keep. I checked a few of the popular ones. Brave's Search API privacy notice, updated earlier this month, says it logs search queries along with your IP address and authentication token for 90 days for billing and abuse prevention, keeps other account data for 12 months after account deletion, requires billing details including a postal address on every plan including the free one, and states that it does not collect identifiers linking a query to an individual or device; a true zero-data-retention option exists but only for enterprise customers. Tavily collects query data plus account identity and usage data, and its policy says that unless your contract says otherwise it may use portions of your query data to improve responses to future queries, and may pass your query on to third-party search index providers when its own index can't answer. That last point is the big structural risk: many APIs, the SERP-scraping ones like SerpApi, Serper and ScrapingDog, forward your query live to Google or Bing, so Google or Bing log the original query no matter what the middleman promises. Brave's own documentation makes exactly this argument for why it can offer real zero retention, because it queries its own index. Firecrawl offers zero data retention only on enterprise terms, with a contact-us flag for crawls. So retention is a contract term, not a default.

How to minimize exposure. Write the query before you send it: have the model produce short generic keywords with no names, addresses, emails, account numbers or document text, then strip anything identifying, and prefer sending your own hand-written keywords over a model-expanded question. Don't paste sensitive document contents into a search-enabled context. Only ask for snippets if you don't need the full page, and skip the fetch tool when snippets are enough. Cache results locally so repeated questions don't re-send the same query. Pick a provider that owns its index, and if retention really matters, get zero retention in writing rather than assuming it. Separate the identity used for the API account from your own: a distinct account, generic billing, and ideally a VPN or outbound proxy so the provider sees a shared egress IP rather than your home one. Turn off telemetry in the local model runtime, which is a separate leak people overlook. Finally, treat everything a search returns as untrusted text: recent research on tool-using agents shows a malicious page can instruct your agent to leak what's in its context through a later tool call, so an agent that can both read the web and read your files is a data-exfiltration path even with a privacy-friendly search provider.

One honest limit: if a question genuinely requires a specific private fact to be searched at all, some disclosure is unavoidable, and the safest move is to not let the agent search on that question.
