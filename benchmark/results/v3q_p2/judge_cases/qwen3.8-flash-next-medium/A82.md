Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

ASSISTANT: Think of them as three different levels of the same stack.

An API is a contract between programs. It's a published surface — endpoints, request and response shapes, error codes, versioning — that says: send me this JSON and I'll give you that JSON back. It predates LLMs entirely, and it knows nothing about them. A REST or gRPC API is designed for a developer who wrote the calling code by hand, once, at build time.

A software tool is the broader idea: any named capability you can invoke to do one job — a library function, a CLI command, a shell script, a calculator. In the agent world a "tool" means something more specific: a capability packaged with three things — a name, a natural-language description, and a typed parameter schema — precisely so a model can read that description at inference time and decide on its own whether to call it and with what arguments. That description field is the whole point. An API doesn't have one; a tool does, because its caller is a language model, not a programmer.

An MCP server is a way to expose tools to LLM applications through one standard protocol instead of bespoke glue. MCP, the Model Context Protocol, is JSON-RPC over stdio or HTTP. A client connects, asks "what do you offer?", gets back tools, and also two other primitives people forget: resources, which are read-only context like a file or a database record, and prompts, which are reusable prompt templates. The current spec, released July 28 of this year, moved to a stateless core and added an extensions framework, multi round-trip requests, and tougher authorization. The value of MCP isn't that it makes tools possible — function calling already does that — it's that one server becomes usable by Claude Code, Cursor, Open WebUI, goose, or your own client, and one client can use any server. Most MCP servers are thin wrappers over ordinary APIs. So: an API is how a service is reached, a tool is a capability packaged for a model to choose, and MCP is the standardized socket that lets a host discover and invoke that tool.

Now the architecture you actually asked about. Four layers.

Layer one is inference. Run the model behind a server that speaks an OpenAI-compatible chat completions endpoint with tool calling — llama.cpp's llama-server, Ollama, vLLM, or LM Studio. Pick a model that's genuinely good at function calling, not just good at prose; the Qwen 3.5, Llama 4 and Gemma 4 families get recommended a lot in current local-agent guides. Be honest with yourself here: small local models are much flakier at tool calling than frontier models. They emit malformed JSON, hallucinate tool names, or answer from memory instead of searching. Bigger helps, but the bigger lever is keeping the tool surface tiny.

Layer two is the agent loop, which is the part people skip. A search tool doesn't give a model the ability to search; a loop does. You send the question plus the tool definitions, the model returns a tool call, your code executes it, you append the result as a tool message, and you go again until the model produces an answer.
