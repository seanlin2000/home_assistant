Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

USER: Explain the difference between an API, an MCP server, and a software tool. If I wanted to give a local LLM the ability to search the web, retrieve webpages, and summarize them, how would you architect the system?

ASSISTANT: I know this material well enough to explain it without looking anything up. Here's how I'd lay it out.

An API is a contract between two pieces of software that already exist. It defines endpoints, inputs, outputs, and error behavior, and you call it the way you'd call any other program: you write code against it. A weather service with a JSON endpoint is an API. The API doesn't know or care that an AI model exists; it's just a stable interface over some capability.

A software tool, in the agent sense, is a unit of capability wrapped so that a model can invoke it. It has three parts: a name and description the model reads, a typed input schema, and an execution step that actually does something and returns a result. A tool is usually thin. Underneath it there's often just an API call, or a shell command, or a function already in your process. The important part is the wrapper: the schema and the description are what let a model decide when to use it and how to fill in the arguments. So an API is the capability, a tool is that capability packaged for a model to reach, and they often overlap completely in practice.

An MCP server is a specific way of packaging tools so they aren't trapped inside one application. MCP, the Model Context Protocol, is an open standard that lets a program expose tools, resources, and prompts over a single connection, using JSON-RPC, typically over a local process or HTTP. The client asks the server "what can you do," the server answers with its tool list and schemas, and the client's model calls them. The value is reuse: write one MCP server for your company's database and every MCP-capable client, whether that's Claude Desktop, an IDE, or your own agent, can use it without a bespoke integration. It also standardizes transport and permissions, which matters when you're letting a model touch real systems.

The tradeoff is context cost. Every tool you expose gets described in the model's prompt, so bolting on ten MCP servers with sixty tools each will crowd out the room you need for reasoning, and it makes tool selection worse. Small, well-described toolsets beat large ones.

For your local LLM system, I'd build it as one agent loop with three small tools rather than three separate services, because search, fetch, and summarize are steps of a single task and summarizing is something the model already does natively.

Start with the runtime: something like Ollama, llama.cpp with its server mode, or vLLM exposing an OpenAI-compatible endpoint with function calling. You need a local model that actually supports tool calls reliably; a 7B model will do simple single-call tasks but gets flaky on multi-step chains, so budget for a larger quantized model if you want this to work without hand-holding.
