## Copilot Studio web search functionality

Copilot Studio agents access the web via Bing APIs through three different mechanisms: specific URLs, open web search, or custom search. You can use these capabilities individually or in combination. Specific URLs act as individual knowledge sources. Open web search is available via the Web Search setting. Or you can use a custom search in a generative answers node. Depending on the maker's configuration, all or a subset of public websites indexed by Bing are searched using the Grounding with Bing Search or Grounding with Bing Custom Search APIs.

## How web search works

When you enable Web Search and a user asks a question, the Copilot Studio agent generates a search query. This query is a brief, focused keyword query derived from the user's question. The Copilot Studio agent then sends this query to the Bing search service. This generated query isn't the full user prompt or conversation, but a distilled set of terms the system determines retrieves relevant info. For example, if the user asks, "What are the latest trends in electric vehicle sales worldwide?", the Copilot Studio agent might send a query such as "latest global electric vehicle sales statistics 2025" to Bing.

Bing processes this query and returns relevant search results (web page titles, snippets, citations). The Copilot Studio agent uses the information from these results to compose a summarized final answer given to the user. It integrates the web content with any other active knowledge sources or actions. The user sees a unified answer combining all relevant information and the cited websites (including links to those websites) that informed the generation of the summary output.

## Web search query logging

Search queries that Copilot Studio agents send to Bing aren't associated with the customer's tenant ID. The query doesn't include any cookies or tracking tokens that could link it to a user session. The Bing service treats the query as an anonymous request from Copilot Studio, preventing any customer-specific profiling.

### For Entra ID authenticated users

For Microsoft Entra ID-authenticated use, the Microsoft Copilot Studio service-specific section of the Microsoft Product Terms provides the following commitments about the generated search queries sent to the Bing search service:

- Microsoft has no rights to them other than as needed to provide the service.
- They aren't used to improve Bing.
- They aren't used to create advertising profiles or to track user behavior.
- They aren't shared with advertisers.
- They aren't used to train generative AI foundation models.
- They're treated as customer confidential information and protected by appropriate technical and organizational measures.

### For all other use cases

If the user isn't Entra ID authenticated, the content of the query is logged to Bing's systems and used according to the Microsoft Privacy Statement including to improve the search service—for example, to refine Bing's ranking algorithms or results quality. Because the queries lack identifiers, this logging can't single out an organization or users. Bing uses the data in aggregate to tune search results but can't attribute any query to any individual or organization.

# # How to add web search to a local AI agent (Ollama, LM Studio, Pi, and Goose)

A local model has no idea what happened after its training cutoff, and most search APIs would put a bill back into your zero-cost stack. This guide covers adding free web search to agents running on Ollama and LM Studio, via LM Studio, Goose, Pi, and Cline, plus the privacy caveat.

Running a model locally solves cost, privacy, and control in one move, and creates a new problem in the same move: the agent's knowledge ends at its training cutoff, and a local machine has no web index. Ask a local Gemma or Llama about a library released last month and you get confident fiction. Web search fills that gap, provided you can add it without reintroducing the API bill your local stack exists to avoid.

Parallel MCP[Parallel MCP] is free with no API key or account, so a fully local agent gains real web search and page fetching for exactly $0. Disclosure: it's ours, which is why this guide uses it; the setup patterns below work with any hosted MCP server if you'd rather bring a different one.

## ## One caveat before setup

Adding web search punctures pure locality: your search queries and fetched URLs go to the search provider, even though your prompts, documents, and the model's reasoning stay on your machine. For most people that's the right trade, since a query is far less sensitive than a conversation. If your threat model forbids even queries leaving the machine, stop here; no hosted search fits, and a local crawler won't give you a web-scale index.

## ## LM Studio

LM Studio runs models locally and speaks MCP natively, with one-click install links (the `` `lmstudio://` `` deeplink in our installation docs[installation docs]) or a manual entry in its `` `mcp.json` ``. Once added, any tool-capable local model can call `` `web_search` `` and `` `web_fetch` `` like any other tool.

## ## Goose

Goose, Block's open-source agent, runs against local models and adds MCP servers as extensions. Use the one-click `` `goose://` `` install link in our installation docs[installation docs], or add an extension manually with type `` `streamable_http` `` and the URL `` `https://mcp.parallel.ai/mcp` ``. It works without a key.

The Pi coding harness pointed at an Ollama model is the purest zero-cost stack, and we've published a complete walkthrough: building a fully free CLI agent with Pi, Ollama, Gemma 4, and Parallel[building a fully free CLI agent with Pi, Ollama, Gemma 4, and Parallel]. ## ## Two tips for small local models

First, keep the tool count low. Small models degrade at tool selection much faster than frontier ones, so a local agent with two well-described tools (`` `web_search` ``, `` `web_fetch` ``) will outperform the same model juggling twenty. Connect to `` `https://mcp.parallel.ai/mcp?tools=web_search,web_fetch` `` and the server exposes only those two. Second, lean on search excerpts. The Parallel server returns excerpts dense enough to answer from directly, which matters doubly when your model's context window is 8k or 32k rather than a million; teach your agent, via system prompt or skill, to fetch full pages only when the excerpts fall short.

**What stays local**

Your prompts and any documents or files you feed the model. The full conversation history and the model's reasoning. Model weights, inference itself, and everything the model does with the results after they come back — including your final answer and any follow-up reading of a page you choose to open locally. Also your identity in the ordinary sense: the search provider never sees the text you asked the model in natural language, only what your agent decides to send as a query.

**What gets transmitted**

The search query itself is the big one, and this is the part people underestimate. Many harnesses don't send your literal question; they have the model distill keywords first. Microsoft's Copilot Studio documentation describes exactly that: the agent generates "a brief, focused keyword query derived from the user's question," not the full prompt or conversation. That sounds reassuring until you notice that a distilled query is often *more* revealing than prose, because it strips away hedging. Ask a local model privately about symptoms of a serious illness and the query that leaves your machine looks like "early pancreatic cancer symptoms survival rate." Your reasoning stayed home; your health concern didn't.

Then there's the metadata layer. Every API call carries your IP address, which reveals your approximate location and your ISP, plus the usual HTTP headers, your user agent string, and a timestamp. If you authenticate with an API key or account — SerpApi, Tavily, Exa, Linkup, Brave, Google Programmable Search all work this way — the provider ties every query to your billing account, so queries stop being anonymous entirely. That's the single biggest change in what they can see: a keyed account turns a pile of queries into a profile with a name and a credit card attached.

Third, URL fetches. If your agent uses a web_fetch or content-extraction tool, that request names the exact page it retrieved. Some providers crawl or re-fetch pages themselves on your behalf, which means the *publisher* of that page sees a bot visit attributed to the provider rather than to you, but the provider still knows you wanted that specific document. Cloudflare's Web Search API documentation notes that requests are routed through your AI Gateway and logged there alongside your inference requests, then forwarded to whichever provider you picked — so logging happens on their side too, not just the search engine's.
