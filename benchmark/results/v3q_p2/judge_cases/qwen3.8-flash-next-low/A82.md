Reference sketch (what a correct answer must contain):
An API is an interface one program offers to others (a web search service's HTTP endpoint, for example). A tool, for an LLM, is a function the model may ask to call, described by a name, a description and an argument schema; the surrounding software runs it and hands back the result. An MCP server speaks the Model Context Protocol, an open standard for offering tools (and resources and prompts) to any compatible client, and often wraps one or more APIs. Architecture: the model served locally; an agent loop that sends the conversation and tool list, runs any tool call, returns the result and asks again; an MCP server with a search tool (calling a search API or SearXNG) and a page-fetch tool (download, extract the main text, cap its size); summarizing done by the model itself from the returned text. Safeguards: a cap on tool rounds, timeouts, treating fetched text as untrusted (prompt injection), and caching.

## Scope
The Model Context Protocol includes the following projects:
- MCP Specification: A specification of MCP that outlines the implementation requirements for clients and servers.
- MCP SDKs: SDKs for different programming languages that implement MCP.
- MCP Development Tools : Tools for developing MCP servers and clients, including the MCP Inspector
- MCP Reference Server Implementations: Reference implementations of MCP servers.
MCP focuses solely on the protocol for context exchange—it does not dictate how AI applications use LLMs or manage the provided context.
## Concepts of MCP
### Participants
MCP follows a client-server architecture where an MCP host — an AI application like Claude Code or Claude Desktop — establishes connections to one or more MCP servers. The MCP host accomplishes this by creating one MCP client for each MCP server. Each MCP client maintains a dedicated connection with its corresponding MCP server. Local MCP servers that use the STDIO transport typically serve a single MCP client, whereas remote MCP servers that use the Streamable HTTP transport will typically serve many MCP clients. The key participants in the MCP architecture are:
- MCP Host : The AI application that coordinates and manages one or multiple MCP clients
- MCP Client : A component that maintains a connection to an MCP server and obtains context from an MCP server for the MCP host to use
- MCP Server : A program that provides context to MCP clients
For example: Visual Studio Code acts as an MCP host. When Visual Studio Code establishes a connection to an MCP server, such as the Sentry MCP server, the Visual Studio Code runtime instantiates an MCP client object that maintains the connection to the Sentry MCP server. When Visual Studio Code subsequently connects to another MCP server, such as the local filesystem server, the Visual Studio Code runtime instantiates an additional MCP client object to maintain this connection. Note that
MCP serverrefers to the program that serves context data, regardless of where it runs. MCP servers can execute locally or remotely. For example, when Claude Desktop launches the filesystem server, the server runs locally on the same machine because it uses the STDIO transport. This is commonly referred to as a “local” MCP server. The official Sentry MCP server runs on the Sentry platform, and uses the Streamable HTTP transport. This is commonly referred to as a “remote” MCP server.
### Layers
MCP consists of two layers:
- Data layer : Defines the JSON-RPC based protocol for client-server communication, including capability and version discovery, and core primitives, such as tools, resources, prompts and notifications.
- Transport layer : Defines the communication mechanisms and channels that enable data exchange between clients and servers, including transport-specific connection establishment, message framing, and authorization.
#### Data layer
The data layer implements a JSON-RPC 2.0 based exchange protocol that defines the message structure and semantics. This layer includes:
- Discovery : Lets clients query a server’s supported protocol versions, capabilities, and identity through the`server/discover` request
- Server features : Enables servers to provide core functionality including tools for AI actions, resources for context data, and prompts for interaction templates from and to the client
- Client features : Enables servers to elicit input from the user. Sampling is deprecated as of protocol version`2026-07-28` .
- Utility features : Supports additional capabilities like notifications for real-time updates and progress tracking for long-running operations
#### Transport layer
The transport layer manages communication channels and authentication between clients and servers. It handles connection establishment, message framing, and secure communication between MCP participants. MCP supports two transport mechanisms:
- Stdio transport : Uses standard input/output streams for direct process communication between local processes on the same machine, providing optimal performance with no network overhead.
- Streamable HTTP transport : Uses HTTP POST for client-to-server messages with optional Server-Sent Events for streaming capabilities. This transport enables remote server communication and supports standard HTTP authentication methods including bearer tokens, API keys, and custom headers. MCP recommends using OAuth to obtain authentication tokens.
### Data Layer Protocol
A core part of MCP is defining the schema and semantics between MCP clients and MCP servers. Developers will likely find the data layer — in particular, the set of primitives — to be the most interesting part of MCP. It is the part of MCP that defines the ways developers can share context from MCP servers to MCP clients. MCP uses JSON-RPC 2.0 as its underlying RPC protocol. Client and servers send requests to each other and respond accordingly. Notifications can be used when no response is required.
#### Statelessness and discovery
MCP is a . Every request carries the protocol version and the relevant to that request in its`_meta` field, so the server can process each request on its own. Clients should also identify themselves in the same field unless configured not to. Servers advertise their supported versions and capabilities through the mandatory `server/discover` request, which clients may send before any other request. Detailed information can be found in the specification, and the example showcases the per-request metadata and the discovery sequence.
#### Primitives
MCP primitives are the most important concept within MCP. They define what clients and servers can offer each other. These primitives specify the types of contextual information that can be shared with AI applications and the range of actions that can be performed. MCP defines three core primitives that *servers*can expose:
- Tools : Executable functions that AI applications can invoke to perform actions (e.g., file operations, API calls, database queries)
- Resources : Data sources that provide contextual information to AI applications (e.g., file contents, database records, API responses)
- Prompts : Reusable templates that help structure interactions with language models (e.g., system prompts, few-shot examples)

## How to Connect Local LLMs (Ollama) with Web Search for Zero-Cost Research Agents
I burned through $40 in API credits in a single afternoon last month, just testing a research agent that kept re-searching the same three queries because I forgot to cache results. That’s when it clicked: if I’m running the model locally anyway, why am I still paying per token for the “thinking” part?
So I rebuilt the whole thing with Ollama on the backend and a free search API bolted on the side. Total cost for a full day of heavy testing: $0.00. Electricity, sure. But no invoice.
This is the setup I landed on, what broke along the way, and whether it’s actually worth your weekend.
## Why Local LLM + Web Search Is Suddenly Viable
Here’s the thing nobody tells you upfront: a research agent isn’t really an “AI problem.” It’s a plumbing problem.
The model doesn’t need to know anything. It needs to:
- Decide what to search for
- Fire off the search
- Read what comes back
- Decide if it needs to search again
- Synthesize an answer
None of that requires GPT-4-class reasoning. A well-prompted 8B or 14B model running locally handles steps 1, 2, and 5 just fine. The “intelligence” bottleneck in RAG-style research agents is almost always the retrieval quality, not the model’s raw IQ.
That reframing matters. Once you stop treating the LLM as the expensive, precious resource and start treating it as a free, always-on router that occasionally calls out to the internet, the economics flip completely.
## What’s Actually Happening Under the Hood
When people say “connect Ollama to web search,” they usually mean one of two architectures, and mixing them up is where most tutorials go sideways.
Architecture A: Tool-calling loop. The model gets a search_web(query) function definition. It decides when to call it, Ollama returns a tool-call JSON, your script executes the actual HTTP request, and the result gets fed back into the context window for the next turn. This is the “agentic” version.
Architecture B: Pre-fetch RAG. You search first, dump the top results into the prompt, then ask the model to answer using only that context. No tool-calling needed — just string concatenation. Dumber, but way more predictable.
💡 In my tests, Architecture B was more reliable for models under 8 billion parameters. Smaller models are inconsistent at formatting valid tool-call JSON, and a single malformed call can silently break your whole loop. If you’re on a 13B+ model with good function-calling support (Llama 3.1, Qwen2.5, Mistral Nemo), Architecture A starts to feel genuinely agentic.
## Picking Your Stack: The Real Options
I tested four search backends over about two weeks. Here’s the honest breakdown.
Search Backend | Cost | Setup Difficulty | Result Quality | Rate Limits
DuckDuckGo (unofficial API) | Free | Easy | Decent, sometimes stale | Loose but unpredictable
SearXNG (self-hosted) | Free | Medium-Hard | Excellent, aggregates multiple engines | None (you own it)
Brave Search API | Free tier (2,000/mo) | Easy | Very good | Hard cap, then paid
Tavily (built for AI agents) | Free tier (1,000/mo) | Easiest | Excellent, pre-summarized | Hard cap, then paid
If your goal is truly $0 forever, SearXNG self-hosted in Docker is the only option with no ceiling. Everything else is “free until it isn’t.”
⚡ What caught me off guard: Tavily’s results come pre-chunked and summarized specifically for LLM context windows, which sounds like a small thing until you realize how much prompt-engineering effort it saves you. It’s the difference between feeding your model a clean paragraph versus a wall of raw HTML soup scraped from a search results page.
If you want to experiment with the API yourself, Tavily’s official documentation is useful for checking the current search API, response structure, and available options.

Pros
- Zero marginal cost once your hardware is paid for — run it 500 times a day if you want
- No rate-limit anxiety with SearXNG, which changes how you use the tool; I stopped batching queries to “save my quota” because there wasn’t one
- Full data privacy. Nothing about your search queries leaves your machine except the actual search request itself, and even that’s routable through your own SearXNG instance
- Surprisingly usable at 14B. Qwen2.5 14B with SearXNG produced answers I’d genuinely trust for a first draft
Cons
- Local inference is slow on consumer hardware. A 70B model on a single RTX 4090 took 40-90 seconds per generation step. Multiply that by a multi-hop research loop and you’re waiting minutes for one answer.

ASSISTANT: Think of the three as different levels of the same problem: how one program asks another to do something.

An API is a contract. It says: here are the endpoints, here's the shape of the request, here's the shape of the response, here's how you authenticate, here's the version. It's designed for a programmer to call. Brave's search API doesn't care why you're calling it or what you'll do with the answer. It's a doorway with a documented shape.

A software tool is a thing that does work. A CLI, an app, a library function. In the specific context of language models, "tool" has narrowed to mean something precise: a named function with a description and a JSON-schema parameter list, which you hand to the model so the model can *decide* to call it, and whose result gets appended back into the model's context window as another message. The interesting part isn't the function; it's that a model chose to invoke it.

An MCP server is a way of packaging tools and data so that any MCP-capable application can discover and call them. The Model Context Protocol is JSON-RPC over either stdio for local processes or streamable HTTP for remote ones. The current spec, the 2026-07-28 release, describes a host, a client per server, and a stateless core where each request carries its own version and metadata. A server advertises what it has through a discovery call, and the client lists primitives and then calls them. Its three server primitives are tools, which are executable actions; resources, which are context data you read rather than execute; and prompts, which are reusable templates. Worth noting if you're reading older tutorials: sampling, where a server asks the client's model for a completion, is deprecated in that version, so new servers should call the model provider directly rather than piggyback on the host.

So the cleanest one-line distinction is: an API is how programs talk, a tool is a unit of work a model can choose to invoke, and an MCP server is a standardized API whose whole purpose is to expose tools and resources to LLM applications. MCP is essentially a tool API with discovery built in, plus descriptions written for a model rather than for a developer.

Now for your system. I'd build it in layers.

The bottom layer is inference. Ollama or a llama.cpp server, exposing an OpenAI-compatible chat-completions endpoint with tool calling. Model choice matters more than people expect. Guides and practitioners converge on roughly thirteen billion parameters and up for reliable function calling — Llama 3.1 and later, Qwen2.5 at fourteen billion, Mistral Nemo. Below about eight billion, models are inconsistent at emitting valid tool-call JSON, and one malformed call silently breaks your loop.

The middle layer is the orchestrator, a small script that owns the loop: send the query plus tool definitions, get back either an answer or a tool call, execute it, append the result, repeat, with a hard cap of maybe four or six calls and a token budget so it can't spin.

The tool layer is three tools. Search takes a query and returns structured JSON — title, URL, snippet, date. Fetch takes a URL, does an HTTP GET with a timeout, then extracts readable text, stripping nav and ads, and truncates to a token ceiling; cache it. Summarize takes that extracted text and produces a compressed summary with the URL attached.
