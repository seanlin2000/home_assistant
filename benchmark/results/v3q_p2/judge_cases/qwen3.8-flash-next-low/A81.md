Reference sketch (what a correct answer must contain):
The search provider sees each query the model writes (which can carry personal details from the conversation), the IP address it came from, the API key and so the account and billing identity behind it, timing and frequency, and request metadata such as the user agent. Websites the assistant then fetches see the IP address and the requests. What stays local: the audio and transcription if speech is processed locally, the full conversation and history, the model's reasoning and answers, and anything never put into a query. Minimizing exposure: keep personal details out of queries (write queries from the question, not the whole conversation), search only when needed, cache results, use a privacy-focused provider or a self-hosted metasearch proxy such as SearXNG, route through a VPN for IP privacy, and check the provider's data-retention terms.

ASSISTANT: Here's the mental model: your local model keeps your data private, but every search call is a small disclosure, and the search provider is the one party you're handing information to.

**What stays local.** Your model weights, your conversation history, your documents, your embeddings, and anything you've cached on disk. Nothing about your corpus leaves your machine unless the agent decides to put it in a query. That's the important part: the provider never sees your documents — only whatever the agent decides to type into the search box.

**What gets transmitted.** Four things, usually. First, the query string itself, which in practice is derived from your prompt or from your documents, so anything the model quotes or paraphrases into that query is now disclosed — names, email addresses, ticket numbers, code snippets, unpublished manuscript language, all of it. Second, your API key, which identifies your account, and since providers require billing details, the account is tied to your name, email, and payment card held by a processor like Stripe. Third, your IP address, which almost all providers keep for bot detection and abuse prevention. Fourth, request metadata: timestamps and request frequency, which can reveal your usage patterns even without the query text. A related risk is page fetching: if your agent uses an extract or "LLM context" endpoint, it also tells the provider which URLs you wanted read, and in some stacks that fetch happens on their servers rather than yours.

**How long they keep it.** I checked a few providers' current policies. Brave Search API's privacy notice, updated this month, says query records tied to your account are retained up to ninety days for billing and troubleshooting, with IP address and auth token used for abuse prevention, and states it doesn't collect identifiers linking a query to an individual; a true zero-data-retention mode exists but only for enterprise customers. SerpApi says search data expires automatically after thirty-one days, with an optional "ZeroTrace" mode that skips storing search parameters entirely, again enterprise-only. Tavily advertises zero data retention and SOC 2 certification, though it hashes and stores session identifiers for multi-step agent workflows. One caveat Brave makes, and it's a good general warning: scraper-style APIs that return Google or Bing results are still submitting your query to Google or Bing, so a provider's own zero-retention promise doesn't cover the whole chain.

**How to minimize exposure.** The biggest lever is query hygiene: rewrite what you need into short, neutral keywords rather than pasting raw text from your files or conversation, and strip names, addresses, and any identifiers before the call. Next, pick a provider whose retention you've actually read, and pay for the zero-retention tier if you're handling anything sensitive. Use the cheapest search depth that works, because fewer follow-up fetches means fewer disclosures. Consider self-hosting a metasearch instance like SearXNG, which removes the third-party intermediary even though upstream engines still see the queries themselves. Route calls through a VPN or your own relay so your home IP isn't the identifying signal. Turn off response caching where the option exists, since caching means your query gets stored for matching later. And keep your API key out of logs and out of anything your local model can see.

One honest limitation: none of this makes the search invisible to the provider at request time — the query is inherently what you're asking them to look up. The realistic goal is minimizing what's in the query, shortening how long it's kept, and breaking the link between the query and your identity. Provider policies do change, so it's worth re-reading whichever provider you pick before trusting it with sensitive material.
